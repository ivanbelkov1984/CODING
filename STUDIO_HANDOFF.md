## Прямой ответ на открытый вопрос («где лежат 24 документа личности»)

Сессия CODING проверила: **в репозитории `CODING` этих документов нет и не
было** — только инженерные файлы приложения. Также проверен Notion,
подключённый к этому аккаунту Claude, через поиск по запросам «Архитектор»,
«карта личности», «Бельков» — **ноль результатов**. Значит документы не в
Notion этого воркспейса.

Вывод: местоположение 24 документов знает только Иван — вероятнее всего это
база знаний/файлы проекта в кабинете Claude, где создавались скиллы
`architect-*` (там это явно упомянуто как «17. Архитектор — системный промпт
кабинета»), либо локальные файлы вне git. **Ни одна из двух сессий не должна
гадать дальше** — ждём, пока Иван назовёт точный источник явно. До этого
момента операции с СОДЕРЖИМЫМ документов не выполняются ни одной стороной —
это не блокирует остальную работу (см. границы ниже).

## Границы (кто что пишет)

1. **Репозиторий `CODING`** (приложение «Архитектор») правит **только сессия
   CODING**. Студия Белькова в него не коммитит и не пушит.
2. **Репозиторий Студии Белькова** правит **только её собственная сессия**.
   Сессия CODING в него не пишет и доступа к нему не имеет.
3. Если Студии Белькова для одной из СВОИХ программ нужно что-то, реализованное
   в «Архитекторе» — она берёт готовый приём из `architect/PATTERN_LIBRARY.md`
   (публичный, версия-агностичный рецепт: свайп-удаление, hairline-глубина
   вместо теней, undo-тост, «результат не тост, а постоянная карточка»,
   пустые состояния с прогрессом, идентичность по стабильному ключу периода).
   Это **читать можно свободно**, редактировать — нельзя напрямую; новый
   проверенный приём из другой программы предлагается через Ивана, чтобы
   сессия CODING добавила его в библиотеку самостоятельно.
4. **Личные данные** (дневниковые записи, 24 документа личности, что угодно
   личное) никогда не коммитятся ни в один из двух репозиториев и не
   вставляются в issues/PR/комментарии ни одной из сессий. Работа идёт со
   СХЕМОЙ данных (см. `architect/PSY_CONTOUR.md` — как устроена разметка
   записи), не с содержимым.

## Как физически читать друг друга

Каждая сессия по умолчанию видит только свой репозиторий. Чтобы Студия
Белькова могла сама открыть этот файл и `PATTERN_LIBRARY.md` без того, чтобы
Иван копировал текст руками — Ивану нужно один раз добавить репозиторий
`ivanbelkov1984/CODING` как читаемый источник в ТОЙ сессии (той же командой,
которой он подключает репозитории). Тогда она сможет сама открывать эти два
файла в начале каждой своей задачи. Обратного (доступа сессии CODING к
репозиторию Студии) не требуется, пока Студия не пишет ничего, что должно
попасть в «Архитектор».

## Журнал передачи хода работы

Правило: **перед началом новой задачи каждая сессия дописывает сюда одну
запись**, а другая сторона (если параллельно не работает — этого физически
не должно происходить, см. ниже) читает последнюю запись **своей и чужой**
стороны, прежде чем что-то менять. Формат строки:

```
### YYYY-MM-DD HH:MM UTC · <сессия: CODING | Студия> · <кратко что сделано>
Состояние: <что сейчас в проде/в ветке, что стабильно>
Дальше: <что осталось / что должна знать другая сторона>
```

**Владелец лично следит, чтобы обе сессии не работали одновременно** — это
не решается автоматически кодом, это дисциплина запуска задач. Журнал ниже
существует именно для того, чтобы при последовательной работе (сначала одна
сессия, потом другая) не пришлось объяснять заново, что уже сделано.
