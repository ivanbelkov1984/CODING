## Правило №1 (обязательное, перед КАЖДЫМ началом работы)

Прежде чем менять что-либо в этом репозитории, сессия обязана:
1. `git fetch origin` и посмотреть журнал: `git log --oneline -20` на актуальной
   ветке (`MAIN` — канон, деплоится в прод) — увидеть все коммиты, сделанные
   ДРУГОЙ стороной с прошлого раза.
2. Для каждого незнакомого коммита посмотреть, что реально изменилось:
   `git show <hash> --stat` / `git diff <твой-последний-известный>..HEAD` —
   не гадать по названию коммита, а прочитать реальный diff.
3. Прочитать последние 2–3 записи в разделе «Журнал» ниже (обе стороны, не
   только свои) — commit diff показывает ЧТО изменилось, запись в журнале
   объясняет ЗАЧЕМ и что осталось незаконченным (это diff не всегда передаёт).
4. Если после этого неясно, безопасно ли продолжать (похоже, что другая
   сторона на середине незавершённой правки) — не начинать, сообщить Ивану.

Это отменяет более раннюю версию этого файла, где было «Студия не коммитит
в CODING» — было неверно, Иван уточнил: пишут обе стороны, защита — через
чтение истории, а не через единоличное право записи.

## Правило №2 — после КАЖДОГО завершения куска работы

1. Коммит с внятным сообщением (что и зачем, не «fix» или «update»).
2. Пуш в `MAIN` (канон/прод) — и в свою рабочую ветку, если она есть.
3. Дописать в конец раздела «Журнал» одну запись форматом ниже — **даже если
   это кажется очевидным из diff**: журнал переживает конкретные коммиты и
   даёт следующей сессии контекст без необходимости расшифровывать историю
   заново.

```
### YYYY-MM-DD HH:MM UTC · <сессия: CODING | Студия> · <кратко что сделано>
Коммиты: <hash1>, <hash2> …
Состояние: <что сейчас стабильно / что в проде>
Дальше: <что осталось / на что обратить внимание следующей стороне>
```

## Про «24 документа» — снято с повестки для этой работы

Проверено точно: строка «24 документа» не встречается нигде в репозитории
`CODING` — только в одном месте на всей системе: в файле навыка
`architect-map-manager/SKILL.md`. Это **навык Claude Code** (готовая
инструкция-методология), а не файл из какого-либо репозитория — навыки
хранятся на уровне аккаунта/окружения и доступны сессии независимо от того,
какой репозиторий к ней подключён. У этой сессии (CODING) точно такой же
набор навыков `architect-*` тоже загружен — можно убедиться самим.

Иначе говоря: **репозиторий у обеих сессий один и тот же** (Иван подтвердил —
второго источника кода нет). Но кроме репозитория Claude Code подгружает ещё
и навыки, и один из них случайно называется так же, «Архитектор», хотя не
имеет отношения к коду приложения: это персональный коуч-координатор,
которому по своему описанию нужны 24 личных документа (биография,
психологический портрет, тень и т.д.) — но это ОПИСАНИЕ САМОГО НАВЫКА,
не содержимое из репозитория. Существуют ли эти 24 документа вообще
где-либо в виде реальных файлов — знает только Иван; если нет, навык
описывает то, что ещё предстоит создать, а не то, что потерялось.

Для работы над кодом `CODING` это не имеет значения: инженерная работа идёт
по схеме данных приложения (`PSY_CONTOUR.md`), а не по личному контенту.
Дальше эту ветку не тянуть — если Иван захочет включить навык-коуча
`architect-map-manager` всерьёз, это отдельный разговор с ним напрямую про
методологию, не про репозиторий.

## Личные данные — правило без исключений для обеих сторон

Дневниковые записи, психоразметка, любой личный контент **никогда** не
попадают в этот репозиторий (и вообще ни в какой git), ни в issues/PR/
комментарии. Работа — только со схемой/структурой данных.
