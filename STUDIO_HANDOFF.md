> Два разных ИИ-контура работают на одного владельца (Иван) над **одним и тем
> же кодом** приложения «Архитектор» (репозиторий `ivanbelkov1984/CODING`):
> эта сессия и сессия «Студия Белькова» (`bot_project`/`belkov-studio`).
> **Обе стороны имеют право менять код этого репозитория напрямую.** Защита
> от коллизии — не «кто-то один главный», а обязательное чтение состояния
> репозитория перед началом любой работы. Владелец лично следит, чтобы обе
> сессии физически не работали одновременно — этот файл нужен, чтобы при
> последовательной работе никто не переписывал то, что уже сделала другая
> сторона, и не откатывал её изменения по незнанию.

## Правило №1 (обязательное, перед КАЖДЫМ началом работы)

Прежде чем менять что-либо в этом репозитории, сессия обязана:
1. `git fetch origin` и посмотреть журнал: `git log --oneline -20` на актуальной
   ветке (`MAIN` — канон, деплоится в прод) — увидеть все коммиты, сделанные
   ДРУГОЙ стороной с прошлого раза.
2. Для каждого незнакомого коммита посмотреть, что реально изменилось:
   `git show <hash> --stat` / `git diff <твой-последний-известный>..HEAD` —
   не гадать по названию коммита, а прочитать реальный diff.
3. Прочитать последние 2–3 записи в разделе «Журнал» ниже (обе стороны, не
   только свои) — commit diff показывает ЧТО изменилось, запись в журнале
   объясняет ЗАЧЕМ и что осталось незаконченным (это diff не всегда передаёт).
4. Если после этого неясно, безопасно ли продолжать (похоже, что другая
   сторона на середине незавершённой правки) — не начинать, сообщить Ивану.

Это отменяет более раннюю версию этого файла, где было «Студия не коммитит
в CODING» — было неверно, Иван уточнил: пишут обе стороны, защита — через
чтение истории, а не через единоличное право записи.

## Правило №2 — после КАЖДОГО завершения куска работы

1. Коммит с внятным сообщением (что и зачем, не «fix» или «update»).
2. Пуш в `MAIN` (канон/прод) — и в свою рабочую ветку, если она есть.
3. Дописать в конец раздела «Журнал» одну запись форматом ниже — **даже если
   это кажется очевидным из diff**: журнал переживает конкретные коммиты и
   даёт следующей сессии контекст без необходимости расшифровывать историю
   заново.

```
### YYYY-MM-DD HH:MM UTC · <сессия: CODING | Студия> · <кратко что сделано>
Коммиты: <hash1>, <hash2> …
Состояние: <что сейчас стабильно / что в проде>
Дальше: <что осталось / на что обратить внимание следующей стороне>
```

## Общие для обеих сторон файлы (не про личные данные — про архитектуру кода)

- `architect/PATTERN_LIBRARY.md` — переносимые UI/инженерные приёмы этого
  приложения (свайп-удаление, глубина без теней, undo-тост и т.д.) — можно
  свободно читать и брать логику для ДРУГИХ программ Ивана. Если родился
  новый проверенный приём в другой программе — допиши сюда сам, коммитом с
  понятной записью в журнале (не нужно спрашивать разрешения на добавление
  в этот файл — он ровно для этого).
- `architect/PSY_CONTOUR.md`, `architect/DNA.md`, `architect/ENGINE.md` —
  схема данных и метод «Зачем?», на которых построена логика приложения.
  Читать перед тем, как менять что-то в психоконтуре/карте смыслов, чтобы
  не разъехаться с уже принятыми решениями.

## Про «24 документа» — снято с повестки для этой работы

Это оказались документы **другой** системы — набора скиллов
`architect-map-manager` + 7 модулей (Personal Life OS), которую Иван
настраивал отдельно от этого приложения. Совпадает только название
«Архитектор» — по коду и данным это два независимых контура. Для работы над
репозиторием `CODING` содержимое этих 24 документов **не требуется вообще** —
инженерная работа идёт по схеме данных (`PSY_CONTOUR.md`), не по личному
контенту. Вопрос, где физически лежат эти документы, — отдельный разговор
с Иваном напрямую про его систему навыков-коуча, не блокирует ничего здесь.

## Личные данные — правило без исключений для обеих сторон

Дневниковые записи, психоразметка, любой личный контент **никогда** не
попадают в git (ни в CODING, ни в репозиторий Студии), ни в issues/PR/
комментарии. Работа — только со схемой/структурой данных.
