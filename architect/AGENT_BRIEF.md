# Полное задание для сессии, присоединяющейся к разработке «Архитектора»

> Для Студии Белькова (и любой другой сессии, которая начинает работать в
> `ivanbelkov1984/CODING`). Цель файла — дать всё нужное, чтобы менять код
> правильно с первого раза, не ломая то, что уже работает, и не переоткрывая
> то, что уже решено. Читать перед первым коммитом в этот репозиторий.

## Что это за приложение

«Архитектор» — личный дневник жизни (PWA): инсайты, сны, сферы жизни,
чек-ины состояния, паттерны, психологический разбор по методу «Зачем?»,
диалог с ИИ-наставником, смысловая карта тем. Не трекер ради красивых
графиков — цель сформулирована в `ENGINE.md`: **действенные персональные
выводы, а не цифры**. Полный контекст — по порядку чтения ниже.

## Порядок чтения (по приоритету, не всё сразу — по мере задачи)

1. **`STUDIO_HANDOFF.md`** (корень репозитория) — протокол совместной работы
   двух сессий над одним репозиторием: обязательно перед КАЖДЫМ началом
   работы (git log + журнал), не только один раз.
2. **`architect/DNA.md`** — почему интеллект «вплетён», а не по кнопке; два
   слоя (локальная сеть связей + периодический AI-синтез).
3. **`architect/ENGINE.md`** — «умный движок»: 7 способностей, что реально
   ценно пользователю (на основе разбора Bearable/Rosebud/Stoic/Oura), чего
   избегать.
4. **`architect/PSY_CONTOUR.md`** — метод «Зачем?» (научный труд владельца):
   как ИИ размечает записи психологически (симптом/функция/вторичная
   выгода/потребность/состояние Я/эмоция/игра/**themes** — смысловые темы) —
   на этом построена смысловая карта и психологический разбор.
5. **`architect/PATTERN_LIBRARY.md`** — готовые переносимые UI/инженерные
   приёмы (свайп-удаление, глубина без теней, undo-тост, «результат не тост
   а карточка», пустые состояния с прогрессом, идентичность по стабильному
   ключу периода) — использовать эти рецепты, не изобретать заново; можно
   пополнять при появлении нового проверенного приёма.
6. **`architect/REFACTOR_BRIEF.md`, `architect/AI_ROUTING_BRIEF.md`** —
   история решений: что и почему было сделано (причинно-следственный слой,
   AI-роутинг с бюджетом, диалог вглубь). Проверить «Статус» в конце файла
   перед тем, как предлагать что-то похожее — вероятно, уже сделано.
7. **`BRANCHES.md`** (корень) — карта веток, источник правды (`MAIN`).

## Жёсткие правила (не обсуждаются, только уточняются у Ивана)

- **Дополнять и улучшать, не переписывать с нуля.** Архитектура утверждена:
  vanilla JS, один слой — один файл (`app.js`, `index.html`, `styles.css`,
  `sw.js`), без фреймворков и сборки npm-пакетов в рантайм.
- **Личные данные никогда не покидают устройство в открытом виде.**
  Дневниковые записи/психоразметка — только localStorage + E2EE-синк
  (AES-GCM, ключ шифрования только у владельца). Ни в коде, ни в
  issues/PR/комментариях личный контент не появляется — ни реальный, ни
  «пример для теста» (тестовые данные — синтетические, не настоящие записи
  Ивана).
- **AI-ключи** — только локально, per-провайдер, per-профиль
  (`aiKeySlot`/`getAiKeyFor` в `app.js`). Запросы идут из браузера
  напрямую в Anthropic/OpenAI/Gemini, минуя сервер приложения.
- **Серверный `ANTHROPIC_API_KEY`** (для триажа фидбэка/дайджестов) —
  только через GitHub Actions secrets, никогда не в коде и не в коммитах.
- **Дизайн** — строго в рамках системы Linear, уже внедрённой
  (`design_guide.md`): монохромная лестница поверхностей, hairlines вместо
  теней, один акцент. Не добавлять цвета/тени/градиенты вне этой системы.

## Обязательный цикл проверки для ЛЮБОГО изменения

```bash
cd architect
node --check app.js                                   # синтаксис
node build.mjs --combined dist/app.html                # собрать одностраничник для теста
npm test                                               # = build + tests/e2e.mjs (сейчас 99/99)
```
Если Playwright не находит браузер в твоём окружении — указать локальный
Chromium через `PW_CHROMIUM=<путь> node tests/e2e.mjs`.

Для изменений в UI — дополнительно скриншот-проверка мобильного вьюпорта
(390×844) в **обеих** темах (light/dark) через Playwright, руками или
маленьким скриптом (`page.evaluate` для сидинга данных, как в
`tests/e2e.mjs`).

Перед коммитом — добавить e2e-проверку на новое поведение (suite должен
остаться зелёным целиком, не только новый тест).

## Деплой

Прод — `https://ivanbelkov1984.github.io/CODING/` через CI → gh-pages,
деплой **только после зелёного CI**. Пуш — в `MAIN` (канон/прод) и, если
есть отдельная рабочая ветка, в неё тоже. Проверка после деплоя:
```bash
curl -s https://ivanbelkov1984.github.io/CODING/sw.js | grep -o "arch-v[a-f0-9]*"
```
и сверить с последним билдом (версия — content-hash, меняется при любой
правке `app.js`/`styles.css`/`index.html`).

## Протокол совместной работы (кратко — полностью в `STUDIO_HANDOFF.md`)

Обе сессии пишут в один репозиторий. Перед началом работы: `git fetch` +
`git log` + прочитать последние записи журнала в `STUDIO_HANDOFF.md`. После
работы: коммит с внятным сообщением + своя запись в журнал. Владелец лично
следит, чтобы сессии не работали одновременно.
