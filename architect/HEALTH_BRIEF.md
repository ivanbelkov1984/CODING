# «Здоровье» — интеграция науки о зависимостях в движок «Архитектора»

> Заказ владельца: «Архитектор здоровья», где физическое и ментальное
> здоровье пронизывает ВЕСЬ функционал — не отдельная фича, а слой,
> который синтезируется со всеми данными (сны, психоконтур, состояние,
> сферы). Источник: научный разбор через Perplexity (нейробиология
> никотина/сахара, петля привычки, доказательные методы цифровой КПТ).

## Честная оговорка про источник

Ядро науки в разборе Perplexity реальное и совпадает с известной
литературой: дофаминовая петля вознаграждения (VTA, никотиновые
рецепторы), десенсибилизация ГАМК-системы при хронической стимуляции,
петля привычки «триггер → действие → награда» (Duhigg), принцип «пик
тяги держится 3–5 минут». Часть ссылок в выдаче Perplexity — не научные
источники (профиль психолога в LinkedIn, маркетинговая страница
компании) — это шум поисковой выдачи, не искажение сути; на итоговую
архитектуру не повлияло.

## Принцип: не отдельная система, а слой поверх существующего движка

Прежде чем писать код, свели науку с тем, что уже работает:

| Концепция из разбора | Уже есть в движке | Что действительно новое |
|---|---|---|
| Триггер → действие → награда (петля привычки) | `smartInsights()` уже считает запаздывающие связи для никотина/кофеина/алкоголя из чек-ина; `crossLinks`/`livingLinks` — кросс-доменные паттерны сфер | Явный лог **момента импульса** (не только факта употребления постфактум) |
| Пик тяги 3–5 минут → пережить, не бороться силой воли | — | Микро-интервенция (дыхание/вода/движение) прямо в моменте лога |
| Предиктивные уведомления ДО срыва | `smartNudge()` уже реагирует на пропущенный чек-ин/сферу | Предиктивный риск-наджер по стрессу/сну — до, не после |
| Когнитивная реструктуризация (вторичная выгода) | Психоконтур (метод «Зачем?» владельца) **уже** делает ровно это: symptom → func → gain → need | Ничего нового — переиспользуется как есть, отдельная кнопка-вход из «Здоровья» |
| «Что влияет» на состояние | `smartInsights()` уже фильтрует по никотину/алкоголю/кофеину | Добавлено «сладкое» как 4-й фактор чек-ина |

Итог: около 60% фундамента уже был в движке (Bearable-паттерн
запаздывающих связей, метод «Зачем?»). Новое — конкретная сущность
«Тяга» и предиктивный наджер, плюс единая точка синтеза (раздел меню).

## Фаза 1 (сделано, этот брифинг)

1. **Чек-ин**: добавлено «Сладкое» — 4-й булев фактор рядом с никотином/
   кофеином/алкоголем; `smartInsights()` считает связь автоматически.
2. **«Тяга»** (`DB.cravings`): лог импульса — что тянет, триггер
   (свободный текст), сила 0–10 (слайдер). При силе ≥6 — инлайн-подсказка
   с 3 микро-интервенциями (дыхание/вода/движение), пока пик не пройдёт.
   Исход — «Устоял(а)» / «Сорвался(лась)», без осуждения при срыве
   (честные данные, не провал — тон метода «Зачем?»).
3. **Предиктивный наджер**: если сегодня стресс ≥7 или сон <6ч и есть
   привычка-сфера/история тяги — предупреждение до срыва: «риск тяги
   выше обычного» → сразу интервенция.
4. **Раздел «Здоровье»** (новая вкладка сайдбара): вредные привычки
   (сферы-трекеры «Без сигарет»/«Без сладкого»/«Без алкоголя», быстрый
   старт одной кнопкой), лог тяги и паттерн (% устоял, частые триггеры),
   «Что влияет на состояние» (переиспользует `smartInsights`), вход в
   психологический разбор (переиспользует «Психика», не дублирует),
   быстрый старт трекера витаминов/добавок (сфера-привычка).

## Фаза 2 (сделано) — синтез второго брифинга (JITAI, 2604 строки)

Второй брифинг (Perplexity) — на порядок крупнее первого: полная
архитектура JITAI (Just-in-Time Adaptive Intervention) для курения и
сахара — event-sourcing БД, REST API, ML relapse-prediction (XGBoost →
Bayesian NN → conformal uncertainty), 5 «обязательных» клинических
концепций (AVE, BCTTv1, passive phenotyping, типология тяги,
variable-ratio reinforcement), 4-уровневый evaluation framework,
онбординг/progressive-profiling, и разбор именования модулей
(Пульс/Триггеры/Риск/Опора/Маршрут/Среда/Разбор/Прогресс).

Прочитан полностью, без пропусков. Ниже — что взято и почему, что
осознанно НЕ взято и почему, а не молчаливое игнорирование.

### Принцип синтеза (как и в фазе 1)

Тот же фильтр: не копировать инфраструктуру брифинга буквально, а
взять science + UX-паттерны и уложить их на архитектуру, которая
реально есть — vanilla JS PWA, один пользователь на профиль, локальный
+ E2EE-синк, без сервера приложений для личных данных, без нативных
разрешений (это веб, не iOS/Android-приложение).

### Взято и реализовано

| Концепция брифинга | Где реализовано |
|---|---|
| Типология тяги: cue-induced (внезапно) vs tonic (фоновое, копится) — разное вмешательство | Шит «Тяга»: необязательный переключатель «Внезапно, от повода» / «Копилось весь день» → разные подсказки (`CRAVING_TIPS_CUE`/`CRAVING_TIPS_TONIC`); фоновая тяга получает физиологическую компенсацию (вода/еда/отдых), не дыхание-от-соблазна |
| Стресс + одиночество — два корневых триггера для обеих зависимостей | Необязательный тег «Один(на)» / «С людьми» в логе «Тяги»; при ≥3 записях «один» и ≥2 «с людьми» — честная корреляция «срывы чаще, когда один(на)» на «Здоровье» (не раньше — чтобы не врать на 2 точках) |
| «Риск» как объяснимый output decision model, не чёрный ящик | Новая карточка «Риск сейчас» вверху «Здоровья» — те же причины, что видит наджер (`riskReasons()`, общая функция, не дублирование логики) |
| BCTTv1: Action Planning («если Х, то Y») | «+ план «если...то»» у самого частого триггера — сохраняется как обычный инсайт (тег «Личное», без новой сущности), всплывает в отклике на следующую тягу с тем же триггером |
| BCTTv1: Restructuring Physical Environment | Раздел «Среда»: 3 простых переключателя (дома нет сладкого/сигарет, вечерний ритуал заменён) — `DB.env` |
| AVE (Abstinence Violation Effect): не красный экран провала, % вместо жёсткого стрика | Уже было в фазе 1 (`reactToCraving`: «записано честно — не провал», % устоял как основная метрика) — здесь только подтверждено и не тронуто, брифинг №2 это же и рекомендует |
| Variable-ratio reinforcement | Отклик на «устоял» иногда (не всегда, ~30%, непредсказуемо) добавляет бонус-строку — специально не по расписанию |
| Модульная карта имён (Пульс/Триггеры/Риск/Опора/Среда/Разбор/Прогресс) | Использованы как **подписи секций внутри одной вкладки «Здоровье»**, не как 7 новых пунктов сайдбара — см. решение по IA ниже |

### Решение по меню/IA — и почему не 7 новых вкладок

Брифинг прямо предлагает 7–8 отдельных «модулей» как первоклассные
экраны. Это разумно для многопользовательского health-tech продукта с
командой поддержки экрана на каждый модуль. Для «Архитектора» это
было бы шагом назад: изначальная жалоба владельца в начале этой самой
сессии — «всё разрозненно и неудобно пользоваться», и добавление ещё
7 пунктов в сайдбар прямо этому противоречит.

Решение: имена модулей (Пульс, Триггеры, Риск, Опора, Среда, Разбор,
Прогресс) стали **подписями секций одной вкладки «Здоровье»**, в
порядке, который брифинг сам называет лучшим пользовательским потоком
(риск → прогресс → опора → триггеры → среда → разбор). «Пульс» отдельным
разделом не сделан — это уже существующий чек-ин на «Сегодня», второй
вход не нужен. «Маршрут» (долгосрочный план/этапы) не сделан — избыточен
для одного пользователя без multi-stage программы; при необходимости
можно добавить позже как ещё один раздел, не как вкладку.

### Осознанно НЕ взято (и почему)

- **Postgres event-sourcing схема** (`context_events`/`behavior_episodes`/
  `trigger_inferences`/materialized views) — рассчитана на серверный
  multi-user backend. У «Архитектора» весь личный контур — локальный
  массив + E2EE-синк на один профиль; `DB.cravings` с полями
  `onset`/`alone`/`trigger` — это и есть посильный эквивalent
  raw-events+episode в одной записи, без лишнего слоя.
- **REST API** (`/checkin`, `/events`, `/interventions/request`,
  `/analytics/risk-status`) — нет и не будет серверной части для личных
  данных; это прямо противоречит правилу сессии «дневниковое — только
  локально + E2EE, никогда через сервер приложения».
- **ML relapse-prediction** (XGBoost/LightGBM, feature store, scheduled
  scoring, model retraining, anti-overfitting policy, time-based
  validation) — требует тренировочный пул данных многих пользователей;
  для одного человека на локальном хранилище это не работает и не
  нужно. `riskReasons()` — rule-based эквивалент decision-engine
  скелета из брифинга (`isEligible`/`chooseIntervention`/`scoreRisk`),
  ровно того размера, который оправдан.
- **Bayesian NN / conformal prediction / uncertainty quantification** —
  бессмысленно без модели, которую нужно калибровать; сам брифинг
  прямо пишет, что это «не первая production-модель», а надстройка
  поверх зрелого ML-пайплайна, которого здесь нет и не планируется.
- **Passive digital phenotyping** (screen-time API, GPS, wearables/HRV) —
  веб-PWA не имеет нативной модели разрешений для этого; добавление
  такого трекинга без явного, осознанного согласия пользователя также
  противоречило бы принципу «ничего лишнего не собираем без явной цели».
- **Микрорандомизированные испытания (MRT)** — метод для доказательной
  проверки политики вмешательства на популяции; бессмысленно при n=1.
- **Event-driven progressive-profiling backend** (Question Catalog/
  Trigger Engine/Answer Store/Profile Composer как отдельные таблицы и
  правила-конфиги) — сама *идея* (короткие контекстные вопросы после
  события, а не анкета при регистрации) ценна и уже используется
  подходом «Здоровья» (например, вопрос «один или с людьми» — не
  обязательный экран, а необязательный тег в моменте); полноценный
  generic rule-engine для одного пользователя — преждевременная
  абстракция.
- **Онбординг-мастер с 4 стартовыми вопросами** — не реализован
  отдельным флоу: «Архитектор» уже не greenfield-регистрация, а
  используемое приложение с историей данных; cold-start профиль здесь
  не нужен так остро, как для нового пользователя health-app с нуля.
  Если/когда понадобится — это отдельная, более простая задача (не
  требует Question Catalog).

### Дальше (не сделано, стало ясно из брифинга №2, следующий брифинг)

- Психоконтур (`i.psy.need`) статистически не пересечён с историей
  «Тяги» — брифинг подтверждает ценность (BCTTv1 identity-language,
  «я не курю» вместо «я пытаюсь бросить») — можно подмешать позже.
  «Витамины/добавки → эффект» — по-прежнему просто сфера-привычка.

## Приватность

Без изменений к общему правилу: `DB.cravings` — тот же локальный +
E2EE-синк контур, что и остальные данные. Ничего не уходит на сервер
приложения. Разбор психоконтуром (когда используется) — по ключу
пользователя, напрямую браузер → провайдер, как и весь остальной ИИ-слой.
