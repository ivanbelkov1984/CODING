# Модель безопасности «Архитектора» — брифинг для GPT (архитектора)

> Назначение файла: чтобы GPT ставил задачи ПО ФАКТУ. Многое из
> предложенной E2EE-архитектуры в «Архитекторе» уже реализовано —
> не нужно переспецифицировать существующее. Здесь — что есть, где
> честная граница, и что реально осталось.

## TL;DR для GPT

Твоя схема (iPhone → Web App → зашифрованный vault; сервер видит только
шифроблоки; расшифровка в браузере по мастер-фразе; GitHub — только код)
**уже реализована** в коде (`architect/app.js`, слой шифрования и синка).
Это не будущее, а текущее состояние — при условии, что задана парольная
фраза. Поэтому задача не «построить E2EE», а «довести и честно назвать».

## Что уже есть (проверено в коде)

- **E2EE-хранилище.** Парольная фраза → PBKDF2 (SHA-256) → ключ AES-GCM-256.
  Если фраза задана, **весь бандл шифруется в браузере**; на сервер
  (Railway) уходит только `{ salt, iv, ct }` — бессмысленный шифроблок.
- **Ключ не покидает устройство.** Фраза — в localStorage профиля, на
  сервер не отправляется никогда. Расшифровка — только в браузере.
- **Телефон — тонкий клиент.** Новый телефон + фраза → вся память назад.
- **GitHub — только код.** Никаких пользовательских данных в репозитории
  (жёсткое правило, соблюдается).
- **Мультипрофильность, слияние без потерь** (CRDT-подобное: union по id,
  побеждает свежая метка `_u`, «надгробия» для удалений).

## Честная граница №1 — ИИ-слой (это НЕ покрывается шифрованием)

Психоконтур, диалог-наставник, сонник, «Разобрать бережно» и т.п.
отправляют **выбранный текст в открытом виде** ИИ-провайдеру
(Anthropic/OpenAI/Gemini) по ключу пользователя. Иначе нельзя — ИИ
обязан прочитать текст, чтобы его разобрать.

Следствия для формулировок (важно не переобещать):
- ✅ Правда: «хранилище end-to-end зашифровано; сервер/разработчик/GitHub
  не видят память в открытом виде».
- ❌ Неправда: «даже ИИ не может прочитать». ИИ видит ровно тот текст,
  который пользователь ему шлёт.
- Два разных Claude: тот, что **пишет** приложение (dev-сессия) — данных
  и ключа не видит; тот, что приложение **вызывает** для разбора — видит
  присланный фрагмент.

Корректный маркетинг-тезис (защитимый):
> «Твоя память end-to-end зашифрована — на сервере только шифроблоки.
> ИИ-разбор идёт по твоему собственному ключу, только по тексту, который
> ты сам выбрал, и никогда не через наш сервер.»

## Честная граница №2 — условность и восстановление

- Гарантия «включена» ТОЛЬКО если задана фраза. Без фразы синк уходит в
  открытом виде. → делаем шифрование форвардным + предупреждение.
- Настоящий E2EE не имеет «сброса пароля»: забыл фразу + на сервере
  только шифроблок = потеря. → нужен **ключ восстановления**.

## Крипто-детали (для точных задач)

- KDF: PBKDF2-SHA256. Итерации подняты до 600 000 (OWASP 2023); старые
  блоки v1 (100k) читаются по-прежнему — обратная совместимость.
- Формат v2 — **конверт (envelope)**: случайный DEK шифрует данные, DEK
  заворачивается фразой И (опционально) ключом восстановления. Это и даёт
  восстановление без «второй копии всех данных».
- Шифр: AES-GCM-256 (аутентифицированный), случайные salt(16)/iv(12).

## Что НЕ берём и почему (чтобы GPT не ставил такие задачи)

- **Presidio / spacy PII-маскировка** — тяжёлая серверная NLP; ИИ-слой и
  так шлёт текст по ключу пользователя. Возможен лёгкий локальный проход
  (телефоны/почта) как единый слой — но это отдельная задача, не Presidio.
- **LangChain / LlamaIndex / серверный RAG / DeepEval-CI** — нет backend
  для логики и нет Python-CI; RAG уже сделан «lite» локально, eval — в
  духе через e2e (Playwright).
- **Хостовая вектор-БД** (Pinecone/Qdrant/Weaviate) — избыточна для ~12
  методов, тянула бы личное на сервер.

## Что реально осталось (сюда ставить задачи)

1. Ключ восстановления (envelope v2) + флоу «войти по ключу». [делается]
2. Форвардное шифрование: предупреждать при несифрованном синке. [делается]
3. Честный privacy-экран в приложении (включая ИИ-исключение). [делается]
4. Позже: единый лёгкий PII-слой перед любой отправкой в провайдер;
   биометрия (WebAuthn PRF) как разблокировка ключа; богатый State
   Extractor → события для JITAI.

## Одной фразой для GPT

Не проектируй E2EE с нуля — он есть. Проектируй поверх: восстановление,
честные формулировки (с ИИ-сноской), UX доверия. Данные пользователя
живут в зашифрованном пространстве на сервере синка; код, интерфейс,
skills и промпты — в GitHub; ИИ-разбор — по ключу пользователя, вне
нашего сервера.
