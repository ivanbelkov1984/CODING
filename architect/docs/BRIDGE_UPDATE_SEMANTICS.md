# Явная update-семантика внешнего моста (Variant B)

Реализация owner decision «VARIANT B — EXPLICIT UPDATE SEMANTICS».
База: MAIN `6dff90a`, ветка `claude/bridge-update-semantics`, отдельный Draft PR.
Закрывает P3 (изменение источника было невидимо), P1 (смешение единиц
пакеты/записи в UI) и латентный дефект дублирования sourceId внутри feed.

## 1. Контракт идентичности

- Идентичность записи — **только семантический `sourceId`**. Один sourceId =
  одна canonical-запись, каким бы каналом/пакетом/контейнером он ни пришёл.
- Изменённый payload того же sourceId — **новая версия той же записи**
  (`changed`), а не новая запись: правка текста в источнике не создаёт
  «#rev2».
- Похожесть текста и content-hash **никогда** не участвуют в идентичности:
  одинаковый текст с разными sourceId — две записи; изменившийся текст с тем
  же sourceId — одна.
- Обновлять **содержимое** записи может только её первичный источник
  (primary sourceId входящей сущности = primary `ext.sourceId` записи).
  Совпадение через псевдоним (кросс-модульная ссылка LIFE↔DREAM↔PARA) —
  это дописывание provenance-ссылок, а не новая версия: проекция другого
  модуля не затирает содержимое и claim-слои первичного источника.

## 2. Обнаружение версии: `ext.entityHash`

При каждом импорте на запись пишется `ext.entityHash` — SHA-256
канонизированного содержимого сущности источника: `type`, `data`,
нормализованные `claimClass`/`claimClasses`, `textOrigin`, `sourceDate`,
`sourceDateRange`, `sourceExcerpt`. Provenance-метаданные (label, module,
clientRef, sourceRefs) в хеш не входят — их изменение не версия содержимого.

Классификация найденной по provenance записи:

| Условие | Статус |
|---|---|
| `entityHash` совпал | `existing-by-provenance` — ноль мутаций |
| Версия изменилась, пользователь не трогал import-owned поля | `changed` — безопасное обновление |
| Версия изменилась, но есть локальные правки import-owned полей | `changed-conflict` — по умолчанию сохраняются локальные значения |
| Обновление добавляет фактический claim-класс, которого не было | `update-rejected` — запись не меняется |
| Материальных отличий нет (включая legacy) | `existing-by-provenance` |

## 3. Владение полями (field ownership)

- **import-owned** — статические списки `EXT_IMPORT_OWNED` по каждому типу
  (для psy-типов — payload-поля общего write-contract `PSY_BUILDERS`);
  только их обновляет повторный импорт.
- **user/local-owned** — всё остальное: `links`, `media`, `cnt` паттерна,
  лайфцикл-`status` relationshipContext, служебные `id/createdAt/day/sv/_u`,
  отображаемые `date/dt/src`. Импорт их не пишет никогда.
- **derived** — движки (Unified Intelligence, mind-body, smartInsights)
  пересчитываются на чтении; персистентных кэшей над импортируемыми
  коллекциями нет, поэтому stale-производных после update не существует.

Детектор локальных правок: при импорте пишутся `ext.importedFields` (имена
import-owned полей) и `ext.importHash` (SHA-256 их значений в записи как
записано). Совпадение текущего хеша со снимком доказывает «пользователь не
трогал» → безопасный `changed`. Расхождение → владение изменившегося
значения неатрибутируемо → `changed-conflict` (не угадываем).

Legacy-записи (импортированы до Variant B, снимков нет): идентичные поля →
`existing`; расхождение только claim/provenance-слоя (ext правит только
импорт) → безопасный `changed`; расхождение полей записи → `changed-conflict`.

Volatile-поля с fallback «на сейчас» (`sphereLog.date`, `psyGoal.startedAt`,
`psyInterventionEpisode.dateTime`, `psyObservation.timestamp`): если новый
payload их не задаёт, обновление сохраняет прежнее значение — повторный
импорт не сдвигает даты на день импорта (`EXT_VOLATILE_WHEN_ABSENT`).

## 4. Терминальная модель исходов (owner review, blockers 1–2)

Пакет/подача считаются обработанными (журнал + чекпойнт) **только когда все
элементы терминальны**:

| Исход | Терминальность |
|---|---|
| new (применён), changed (применён), existing, merge ссылок | терминальный |
| explicit keep-local, explicit override | терминальный (решение записано) |
| `changed-conflict` без решения | **блокирующий**, всплывает при каждом чтении |
| `update-rejected` (claim-эскалация) | **блокирующий**, всплывает, пока источник не исправлен |
| conflict идентичности, invalid, unresolved refs | блокирующие (как в Wave 6) |

**Мост (`selection = null`):** `changed` применяется после явного
подтверждения («Да, импортировать и обновить», число обновлений названо).
Если подача содержит хотя бы один `update-rejected` или неразрешённый
`changed-conflict` — **вся подтверждённая подача останавливается
fail-closed ДО любой работы**: canonical, журнал и чекпойнт не меняются ни
на байт; safe-changed и new из этой же подачи тоже не применяются (один
item не может «оплатить» проглатывание другого — владелец подтверждает
подачу одной кнопкой целиком). Оба состояния всплывают при каждом
следующем чтении источника.

**Ручной импорт пакета:** каждый `changed-conflict` требует явного
per-record решения — «Оставить мою версию» / «Заменить версией источника»
(радио-выбор, **ни один вариант не выбран по умолчанию**; снятый чекбокс
решением не является). Без решения по каждой конфликтной записи commit
отклоняет пакет целиком — «новая» запись не может протащить пакет в журнал
мимо конфликта.

- **Explicit override** — обычное обновление с `mode: 'override'` в
  revision provenance; терминально (replay той же версии → existing).
- **Explicit keep-local** — терминальное решение с provenance в
  `ext.localResolutions[]`: `{entityHash отклонённой версии, packageHash,
  resolvedAt}` — старый приватный текст версии источника НЕ хранится.
  Повтор той же версии источника классифицируется как resolved/existing
  (replay детерминирован, чекпойнт может честно двигаться); НОВАЯ версия
  источника (другой hash) снова требует решения.
- **`update-rejected` не применяется никаким выбором UI/API**: commit
  отклоняет весь пакет независимо от selection; в журнал ничего не
  пишется, поэтому событие не может быть «поглощено» ledger-skip'ом.

Claim safety on update: набор классов новой версии не может добавить
фактический класс (`user_fact`, `external_event`, `practice_action`),
которого не было у записи, — `working_hypothesis`→`user_fact`,
symbolic→fact и подобные повышения отклоняются. Снятие класса
(де-эскалация) разрешено. Parse-guard A7 (assistant_interpretation ×
фактический слой) действует без изменений.

## 5. Revision provenance

Каждое применённое обновление пишет в `ext`:

- `entityHash`, `importHash`, `importedFields` — новые снимки;
- `importUpdatedAt`; `importedAt` первого импорта сохраняется;
- `revisions[]` (bounded, последние 10): `{at, packageHash, sessionRef,
  prevEntityHash, entityHash, updatedFields, mode: update|override}` —
  полный текст старых версий сознательно не хранится (решение владельца);
- `localResolutions[]` (bounded, последние 10) — терминальные keep-local
  решения: `{entityHash, packageHash, resolvedAt}`, без старых текстов;
- `_u = Date.now()` — обновление переживает merge/sync.

Журнал импорта (`externalWorkSessions`) дополнен `updatedCount`,
`updatedRefs[{coll,id,updatedFields,mode,prevEntityHash,entityHash}]` и
`keptLocalRefs[{coll,id,entityHash,resolution:'keep_local'}]` (ТОЛЬКО
явные решения) — аудит без дублирования приватных текстов. Всё это
byte-identical переживает зашифрованную резервную копию; replay после
restore не меняет ни одного решения.

## 6. Атомарность и конкурентность

- **Один feed = одна транзакция на одном кандидате.** Планы всех пакетов
  строятся последовательно на общем клоне DB (пакет N видит записи и
  обновления пакетов 1…N-1 — это же закрывает дефект «один sourceId,
  впервые встречающийся в двух пакетах feed, давал дубль»). Apply коммитит
  все пакеты в один клон живой DB; сбой любого пакета просто отбрасывает
  кандидата (живое состояние byte-identical), успех — один swap + один
  persist. Снапшот-restore прежней реализации стал не нужен.
- **Optimistic concurrency (stale preview):** план несёт снимок ожидаемых
  значений import-owned полей; commit сверяет их с живым состоянием.
  Запись изменилась между предпросмотром и Apply → пакет падает → весь feed
  отклоняется, требуется новый предпросмотр. «New»-записи дополнительно
  ре-проверяются на commit против живого provenance-индекса (устаревший
  предпросмотр не создаёт дубль), пакет — против журнала импорта.
- Чекпойнт двигается один раз после успеха всего feed; degraded-путь
  (canonical сохранён, чекпойнт нет) не изменён.

## 7. Delete-семантики нет

Исчезновение объекта из подачи никогда не удаляет canonical-запись
(подтверждено тестом). Отдельная delete/tombstone-семантика сознательно не
добавлена (решение владельца, раздел 6).

## 8. Схема и совместимость

`SCHEMA_VERSION` не менялся (9): все новые поля (`ext.entityHash`,
`ext.importHash`, `ext.importedFields`, `ext.importUpdatedAt`,
`ext.revisions`, ledger-поля) аддитивны, читаются fail-closed и переживают
generic sync/backup как часть записи. Миграция не требуется: legacy-записи
обрабатываются на лету (см. §3). Зашифрованная резервная копия сохраняет
всё byte-identical; replay после restore даёт NEW 0 / CHANGED 0
(подтверждено тестами).

## 9. UI (включая P1-fix)

Предпросмотр моста разводит единицы: «Новых записей», «Будут обновлены»,
«Записей уже существует», «Пакетов уже импортировано (по журналу)»,
«Требуют решения», «Обновлений отклонено». Подтверждение называет число
обновлений. Итог apply отчитывается пакетами и записями раздельно.
Acceptance replay B-01 на этой версии: «Новых записей: 0 · Пакетов уже
импортировано (по журналу): 2».

### 9.1. Экран импорта: три шага и правило видимости

Экран «Импорт данных» построен как три шага: **выбрать файл → увидеть, что
добавится → добавить**. Индикатор шага показывает фактическое состояние, а не
намерение: на шаге 2 в приложении ещё ничего не изменено.

Правила, которые нельзя нарушать (закрыты сюитой `importFlow.spec.mjs` и
мутационной проверкой `importFlow-mutation.mjs`):

1. **Результат разбора никогда не рендерится в свёрнутый блок.** Ровно этот
   дефект делал первый импорт невозможным: выбор файла на чистой установке
   полностью разбирал подачу и рисовал предпросмотр вместе с кнопкой
   применения внутри свёрнутого `<details>` «для продвинутых» — человек не
   видел ответа на своё единственное действие. Контейнеры `#ext-out`,
   `#ext-actions` и `#ext-conn-out` живут в разметке экрана и не могут быть
   спрятаны перерисовкой списка источников.
2. **Данные раньше действия.** Выбор файла и поле вставки стоят в DOM до
   главной кнопки; зона результата — после неё.
3. **Источник не является предусловием.** Одна главная кнопка сама выбирает
   путь: выбран источник — идём через мост (журнал/чекпойнт), не выбран —
   разовая подача. Дедупликация по `sourceId` одинаково работает в обоих
   путях, поэтому отсутствие источника не создаёт дублей. Управление
   источниками уехало вниз в свёрнутый блок «Источники и история импорта»;
   строка над полем файла всегда говорит, куда попадёт этот импорт.
4. **Решение не прячется.** Если хотя бы одна запись в статусе
   `changed-conflict` или `order-unknown`, подробный список раскрывается
   автоматически, а над ним стоит плашка «нужно твоё решение: N». Иначе
   fail-closed-семантика §4 превратилась бы в молчаливый тупик: импорт не
   применяется, а способ его разблокировать не виден.
5. **Язык сводки — разделы приложения.** «Сны», «Практики», «Инсайты»
   (`EXT_COLL_RU`), а не имена коллекций. Технические подробности (sourceId,
   классы утверждений, статусы) остаются в раскрывающемся блоке.
6. **Обещание безопасности стоит в точке решения**, а не только в шапке:
   «Ничего не удаляется и не перезаписывается… пока не нажал „Добавить“, в
   приложении ничего не изменилось».

Изменение затрагивает только слой интерфейса. Формат v1/v2, правила
идентичности, контракт `sourceVersion`, терминальная модель, журнал импорта,
чекпойнт, атомарность, шифрованная копия и синхронизация не менялись;
`SCHEMA_VERSION` не менялся. Доказательство неизменности семантики: сюиты
`wave6-external-work-bridge` (150), `finalA-bridge` (92), `updateSemantics`
(75) и `revisionOrdering` (49) проходят без единой правки ожиданий.

### 9.2. Поставка архивом (.zip): один архив = одна транзакция

Экран импорта принимает ZIP-архив авторитетной поставки. Архив — ТОЛЬКО
транспорт: он локально (без сети) распаковывается, проверяется fail-closed
и превращается в ОДИН feed `architect-external-work-feed-v1`. Дальше
работает неизменённый мост: кумулятивный предпросмотр всех пакетов на одном
кандидате (пакет N видит результат пакетов 1…N−1), терминальная модель §4,
одно подтверждение владельца, атомарный apply §6 с полным откатом
(canonical, sourceRefs, журнал, чекпойнт). Второго импортёра нет.

Содержимое архива: `FEEDS/*.json` (пакеты v1/v2 или feed-обёртки),
опционально `*MANIFEST.json` (`packages[] {order, file, sha256}` — порядок и
полнота обязательны к согласию с архивом), опционально `SHA256SUMS.txt`
(каждая указанная сумма обязана сойтись; каждый `.json` обязан быть покрыт),
README-текст. Манифест и README — метаданные поставки, канонической
информацией не являются. Без манифеста порядок — числовая сортировка имён.

Fail-closed (ноль мутаций, внятная причина): битый архив/central directory,
шифрование, zip64, multi-volume, небезопасные имена (`..`, абсолютные пути,
дубли), CRC/размер записи, несовпавшая SHA256, отсутствующий или лишний
файл против манифеста, битый JSON, неподдерживаемый format, двойная
поставка одного пакета, лимиты. Лимиты (мобильные): архив ≤ 16 МБ, файлов
≤ 64, распакованный файл ≤ 8 МБ, сумма ≤ 32 МБ, итоговый feed — лимиты
моста (≤ 50 пакетов, ≤ 8 МБ текста). Формат файла определяется по
сигнатуре содержимого, не по имени.

Если источник не выбран, он создаётся автоматически из имени поставки
(kind `external_connector`) — журнал и чекпойнт работают как обычно; до
подтверждения canonical/журнал/чекпойнт/sourceRefs не меняются ни на байт.
Предпросмотр батча живёт только в памяти: перезагрузка страницы требует
выбрать архив заново (устаревший предпросмотр не коммитится вслепую).

UTF-8 BOM в файлах поставки срезается при декодировании (транспортная
деталь, не содержимое). Строка вне закрытого enum-словаря по-прежнему
безопасно приводится билдерами к «unknown»; предпросмотр теперь честно
показывает счёт таких полей («Полей будет приведено к безопасному значению
„неизвестно“: N») по узкой документированной карте
(psyInterventionEpisode.adherence/outcomeClass/acceptability,
psyObservation.entryMode). Словари НЕ расширяются, семантика не меняется.

Сюиты: `importZip.spec.mjs` (транспортные отказы, порядок манифеста,
кумулятивные зависимости, идемпотентность, откаты, копия/restore, a11y,
privacy canary) и `importZip-mutation.mjs` (снятая защита обязана уронить
свой сценарий). SCHEMA_VERSION не менялся.

## 10. Производительность (P2)

Бенчмарк 10 000 записей + 50 пакетов mixed NEW/EXISTING/CHANGED
(Chromium, тот же сценарий на обеих сборках):

| Метрика | MAIN `6dff90a` | Variant B |
|---|---|---|
| preview смешанного feed | 2671 мс | 1167 мс |
| apply смешанного feed | 18633 мс | 295 мс |
| replay preview (checkpoint) | 2750 мс | 242 мс |

Причина: один клон DB и один persist на feed вместо клона+persist на каждый
пакет; пропуск checkpoint/ledger-известных пакетов до построения плана.
Семантика при этом строже (50 changed видны и применяются, а не молча
считаются «existing»).

## 11. Альтернативы, отклонённые в X10

- **Diff/similarity-модель обновления** (сопоставление по тексту) —
  нарушает запрет text-identity; отклонено.
- **Полная история версий с текстами** — владелец явно не требует; хранение
  приватных старых текстов увеличивает поверхность приватности; хеши +
  имена полей достаточны для аудита.
- **Bounded batches 10–20 вместо одной транзакции** — одна транзакция
  оказалась одновременно проще (нет снапшот-restore) и на порядок быстрее;
  покрыта тестами и мутациями, migration risk нулевой (структура данных не
  менялась).
- **Обновление содержимого по alias-совпадению** — затирало бы многослойный
  claim-набор первичного источника более бедной проекцией; запрещено
  (primary-only update rule).

## 13. Rollback

Один revert-commit возвращает MAIN к состоянию до Variant B. Данные,
записанные новой версией, останутся с дополнительными ext-полями — старый
код их игнорирует (обратная совместимость чтения `ext` сохранена), записи
и журнал остаются валидными.

## 14. Кросс-модульная проверка derived-состояния

Персистентных кэшей производных результатов над импортируемыми коллекциями
в приложении нет: Unified Intelligence (Wave 4), Mind–Body (Wave 9),

существует нигде в canonical (закреплено тестом «после update старая
версия НЕ существует нигде») — invalidation-механизм не требуется, новые
engines не добавлялись.

## 15. Упорядочение версий источника (owner decision §19)

`sourceId` = identity · `entityHash` = fingerprint версии содержимого ·
**`sourceVersion` = ordering evidence**. Порядок версий НИКОГДА не выводится
из похожести текста, даты события (`sourceDate`), даты сессии/экспорта,
порядка пакетов в feed или часов устройства.

**Контракт (аддитивно в v1/v2, без version bump):** сущность МОЖЕТ нести
`sourceVersion: { sequence?, modifiedAt?, revisionId? }`:
- `sequence` — монотонный номер ревизии (наличие = заявленная коннектором
  гарантия монотонности);
- `modifiedAt` — source-side время изменения ИСТОЧНИКА (ISO), не время
  экспорта и не дата события;
- `revisionId` — opaque идентификатор ревизии провайдера; сравнивается
  только на равенство.
Bump протокола не потребовался: поле опционально, единственный consumer —
сам мост, отсутствие поля включает fail-closed legacy-путь (см. ниже).

**Детерминированное сравнение (`extCompareSourceVersions`)** по приоритету
владельца: sequence → modifiedAt → revisionId-равенство → известные
исторические хеши (`revisions[]`) → unknown. Равный `modifiedAt` двух разных
ревизий порядок НЕ доказывает (unknown). Метаданные ВЫШЕ исторических
хешей: доказанно более новая ревизия со старым содержимым — сознательный
revert источника → обычный CHANGED, не stale.

**Классификация для same sourceId:**

| Условие | Статус | Терминальность |
|---|---|---|
| тот же entityHash | EXISTING | терминальный |
| версия доказанно старее (metadata) ИЛИ hash ∈ истории ревизий без metadata | `stale-source-version` | **блокирующий**, non-applicable (никакой selection; «восстановить старую версию» — отдельный будущий UX) |
| старая версия, когда более новая установлена ЭТОЙ ЖЕ подачей | `superseded-in-feed` | терминальный skip (newest wins при любом порядке пакетов) |
| та же ревизия + другой hash + другой normalizerVersion | `normalization-change` | **блокирующий** (смена парсера ≠ изменение источника) |
| та же ревизия + другой hash + тот же normalizerVersion | `source-version-conflict` | **блокирующий** (ошибка коннектора/повреждённая подача) |
| доказанно newer + без локальных правок | CHANGED | терминальный при применении |
| доказанно newer + локальные правки | CHANGED_CONFLICT | явное решение |
| содержимое отличается, порядок недоказуем | `order-unknown` | **блокирующий**; явное per-record решение «оставить мою версию» / «заменить версией источника»; claim-guard проверяется до и не обходится |

Две разные версии одного sourceId в одном feed: с ordering evidence —
newest wins детерминированно; без — STOP (array order ≠ temporal truth).

**Normalizer version:** `EXT_NORMALIZER_VERSION` хранится на записи
(`ext.normalizerVersion`); update переносит `sourceVersion` на запись и в
`revisions[]`. Bounded history (10) не ослабляет safety: старый hash вне
истории без метаданных → `order-unknown`, с метаданными → stale.

**Backward compatibility:** create-only пакеты без sourceVersion (включая
B-01) работают как раньше; replay той же версии → EXISTING; известная
старая версия → stale; изменение записи, импортированной без метаданных, →
`order-unknown` до первого явного решения (после keep/override запись
получает актуальные снимки, и версионированные feeds дальше упорядочиваются
автоматически). Claim safety (§4) и защита локальных правок (§3) действуют
поверх ordering без исключений; alias-маршрут по-прежнему не пишет
содержимое — stale-проекция другого модуля не может откатить primary.

## 16. Известные ограничения

- `ext.revisions` и `ext.localResolutions` ограничены последними 10
  записями (полные тексты старых версий не хранятся по решению владельца).
- Update по псевдониму невозможен намеренно (см. §1) — источник, желающий
  обновить запись, обязан адресовать её своим primary sourceId; эскалация
  claim-слоёв в alias-пакете не трогает запись вовсе (объект ему не
  принадлежит, содержимое не пишется).
- Разрешение конфликтов в мосту не делается «на месте»: мост честно
  останавливает подачу и направляет в ручной импорт пакета, где есть
  per-record выбор. Это сознательный trade-off в пользу простого и
  безошибочного UX одной кнопки.

## 17. Инспектор записи и локальная правка (owner decisions, класс B)

### 17.1 Зачем

До этого раздела «Мои записи» показывали одну строку-сводку и кнопку
удаления. Полный текст импортированной записи прочитать было негде, а
единственное доступное действие было разрушительным. Инспектор
(`recOpen` → оверлей `ov-rec-det`) открывает ЛЮБУЮ каноническую запись
целиком: человеческие поля, происхождение и, отдельным свёрнутым блоком,
технический дамп.

### 17.2 Матрица редактируемости (`REC_EDIT`)

Матрица объявлена явно для каждой коллекции из `REC_COLLS` — молчаливого
фолбэка нет (проверяется тестом). `fields` — не подсказка для формы, а
**граница**: писатель игнорирует всё, чего в списке нет, даже при прямом
вызове. `guard` решает, открыта ли правка ПРЯМО СЕЙЧАС (состояние записи).
`build` прогоняет результат через тот же доменный строитель, что
create/import.

**A — правка на месте.** Собственная формулировка владельца, изменение
которой не переписывает факт и не меняет доказательство:

| Коллекция | Поля |
|---|---|
| `insights` | title, body, tag |
| `dreams` | title, body, arch, tone |
| `spiritual` | type, text |
| `evolution` | text |
| `patterns` | type, text |
| `bots` | title |
| `whys` | symptom, function, gain, need, cost, alternative, action |
| `relationshipContexts` | label, roleOrRelation, note |
| `spheres` | name |
| `astroPartners` | label |
| `healthDocuments` | title, note |

**B1 — версионная запись.** `psyFormulations`: пока `status === 'draft'`,
правятся `focus` и `formulation` на месте. После принятия (`active` /
`superseded` / `archived`) правка на месте закрывается: исправление — это
НОВАЯ версия со ссылкой `supersedesId` на прежнюю, принятая история не
переписывается. Гипотезы и факторы правятся формой в разделе
«Психология», где действует проверка классов утверждений. Правка
прогоняется через `PSY_BUILDERS.psyFormulation` — пустая формулировка
отклоняется так же, как при создании.

**B2 — зафиксированное суждение за период.** `psyReviews`: правятся
только тексты-сводки — `methodsAppliedSummary`, `adherenceSummary`,
`outcomeSummary`, `acceptabilitySummary`, `adverseEffectsSummary`,
`confoundersSummary`. Неизменны на месте: `periodStart`, `periodEnd`,
`decision`, `goalRefs` / `formulationRef` / `interventionEpisodeRefs` /
`observationRefs` / `sourceRefs`, `hypothesesStrengthened` /
`hypothesesWeakened`, `limitations` и провенанс. Исправление смысла
решения или доказательств — НОВЫЙ review, заменяющий прежний. Правка
прогоняется через `PSY_BUILDERS.psyReview`.

**B3 — измерение/событие.** Правится только поле-заметка, изменение
которого не меняет измеренный факт:

| Коллекция | Правится | Неизменно на месте |
|---|---|---|
| `moments` | note | valence, activation, emo, время |
| `checkins` | note | sl, sq, cl, st, mv, date |
| `symptoms` | note | name, severity, day |
| `labObservations` | note | testName, valueText, unit, referenceText, laboratory, collectedAt |
| `sphereLogs` | note | sphereId, value, date |
| `measures` | — | name, value, unit — отделимой заметки нет |
| `medIntakes` | — | medId, at, status — отделимой заметки нет |
| `cravings` | — | kind, intensity, trigger, outcome — часть самого события |
| `psyObservations` | — | см. ниже |

**`psyObservations.contextTag` — доказательное поле, а не заметка.**
По нему N-of-1 группирует замеры по условиям эксперимента и сравнивает
фазы. Правка «контекста» молча переназначила бы замер в другое условие,
то есть изменила бы доказательство. Поэтому у наблюдения нет полей,
правимых на месте, и в интерфейсе названа именно эта причина.

**Доменные правила без сырой правки.** `psyInterventionEpisodes` —
доказательные поля (`adherence`, `outcomeClass`, `acceptability`) не
правятся сырым вводом: любое изменение обязано пройти ту же проверку
утверждений, что создание и импорт, и `not_done ≠ not_helpful`
сохраняется. `psyGoals`, `psyAdaptivePlans`, `psyExperiments` — статус
меняется только допустимыми переходами жизненного цикла, произвольной
правки статуса нет. `meds` — план приёма правится в «Здоровье», где
проверяется расписание целиком.

**C — системные и производные.** `externalWorkSessions`,
`externalConnections`, `psyLinks`, `astroCharts`, `chats`: ни правки, ни
удаления, причина показана.

В интерфейсе класс B честно различает два разных состояния: «Правка на
месте недоступна» (с причиной и путём) и «Правится не всё» (с
перечислением того, что останется неизменным).

### 17.2.1 Чего пока НЕТ — и почему

Решения владельца по B описывают путь исправления через **коррекцию /
новую версию**. Сами эти потоки в этом релизе **не реализованы**: доступна
только та правка на месте, которую решения прямо разрешают. Причина
названа честно, а не обойдена.

Для измерений в коде уже есть append-only ядро коррекций —
`addCorrection(coll, targetId, patch, reason)` + проекция
`proj` / `projAll` (оригинал неизменен, «текущее принятое» значение
считается при чтении). Но требование владельца «effective views/derived
engines must use the corrected effective value» выполняется не везде:

| Коллекция | Чтение через `projAll` |
|---|---|
| `moments`, `whys` | да |
| `symptoms`, `measures`, `labObservations` | да |
| `medIntakes`, `cravings` | частично (часть чтений сырые) |
| `checkins`, `sphereLogs`, `psyObservations` | **нет** — все чтения сырые |

Пока `checkins`, `sphereLogs` и `psyObservations` читаются мимо проекции,
включение коррекций для них дало бы расхождение: аудит показывал бы
исправление, а аналитика считала бы по старому значению. Это отдельная
сквозная работа (перевод всех чтений и производных движков на проекцию),
и делать её молча внутри задачи про инспектор — значит поменять поведение
аналитики без отдельного решения владельца. Поэтому:
создание коррекций и новых версий из инспектора — **следующая задача**,
а не тихо пропущенная часть этой.

### 17.3 Инвариант импорта

Правка меняет ТОЛЬКО значение разрешённого поля и `_u`. Не трогается
ничего из: `sourceId`, `sourceRefs`, `sourceVersion`, `claimClass`,
`claimClasses`, `textOrigin`, `ext.entityHash`, `ext.importHash`,
`ext.importedFields`, `ext.revisions`, `ext.localResolutions`,
`ext.normalizerVersion`, `format`, `sourceLabel`, `importedAt` —
блок `ext` остаётся byte-identical.

Следствия (все проверены тестом на реальном мосту):

| действие источника после правки | результат |
|---|---|
| replay ТОЙ ЖЕ версии | `existing` — правка владельца жива |
| более новая ревизия | `changed-conflict` — подача останавливается |
| явное «оставить мою» | правка жива, записано `localResolutions[]` |
| явное «заменить» | версия источника побеждает, записана `revisions[]` c `mode: 'override'` |

Тихой перезаписи работы владельца не существует: единственные пути —
`keep`/`override`, оба явные.

### 17.4 Границы

- Правка НЕ пишет обратно в Google Drive / ChatGPT: при сохранении не
  происходит ни одного сетевого обращения, состояние источника и его
  чекпойнт не меняются.
- Правка не повышает класс утверждения: `claimClasses` и `textOrigin`
  после серии правок и разрешений те же, что при импорте.
- Правка изолирована профилем: соседний профиль в хранилище не меняется.
- Сбой сохранения откатывает запись к снимку — состояние в памяти не
  расходится с диском.
- Синхронизация и резервная копия/восстановление переносят и правку, и
  провенанс без изменений.
- Удаление из инспектора — ровно то же `recDel`/`delUndo`, что из списка:
  тот же tombstone, та же отмена.

### 17.4.1 Строгая типизированная идентичность записи

Идентификаторы в приложении сравниваются через `===` везде — `delUndo`,
`tomb`, ссылки между записями. Инспектор следует тому же правилу:
`recDetRecord` ищет запись строгим `r.id === _recDet.id`. Сравнение через
`String()` схлопнуло бы `id = 1` и `id = "1"` в одну запись: открылась бы
чужая, правка ушла бы не туда, удалилось бы не то. Ради этого же `recArg`
сохраняет разницу число/строка при передаче id в обработчик. Закрыто
регрессией с обеими записями в одной коллекции и мутацией
`id-identity-collapsed`.

### 17.4.2 Пустая правка — не правка

Если ни одно разрешённое поле фактически не изменилось, писатель возвращает
`{ ok: true, noop: true }` и не трогает запись вовсе: ни `_u`, ни
хранилище, ни синхронизацию. Иначе открыть и закрыть форму означало бы
новую метку изменения, лишнюю запись на диск, лишний обмен при синке и
ложное «свежее локально» при слиянии. Человеку показывается «Изменений
нет», а не «Сохранено».

### 17.5 Исправленный продакшн-дефект (найден при работе над инспектором)

На собранном `MAIN 1a859f47` идентификатор записи вставлялся в inline-
обработчик как `JSON.stringify(id)` без экранирования кавычек. У записей
со СТРОКОВЫМ id (`psyUid`: `psyReview-…`, `lab-…`, `healthDoc-…`,
`relctx-…`, `externalWork-…`) атрибут обрывался на первой кавычке:
обработчик становился синтаксически неполным, клик бросал
`Unexpected end of input`, а хвост идентификатора парсился как посторонний
HTML-атрибут. Практически это значило, что **психологические,
лабораторные и документные записи нельзя было удалить из «Моих записей»**,
а после появления инспектора — и открыть. Тот же дефект был в ленте
здоровья (`healthTimelineOpen`).

Исправление: `recArg(v)` — `JSON.stringify` (сохраняет разницу
число/строка, потому что id сравниваются через `===`) плюс HTML-
экранирование кавычек и угловых скобок. `esc` для этого не годится: она
кавычки не трогает. Регрессия закрыта сценарием со строковым id и
сценарием с кавычкой внутри id, и подтверждена мутацией
`string-id-breaks-handler`.

## 18. Единая проекция исправлений (owner decisions §1–§8)

### 18.1 Модель

Оригинал записи **неизменен**. Исправление — отдельное append-only событие
в `DB.corrections`; «текущее принятое» значение вычисляется проекцией при
чтении. Схема события:

```
{ id, kType:'correction', coll, targetId,
  patch: { поле: значение },
  reason, supersedesCorrectionId, origin: 'user'|'import_override',
  createdAt, day, sv, _u }
```

Поддерживают исправления только `CORRECTABLE_COLLS`: `moments`, `whys`,
`checkins`, `sphereLogs`, `psyObservations`, `medIntakes`, `cravings`,
`symptoms`, `measures`, `labObservations`. Для остальных коллекций
`addCorrection` отклоняется, а `proj` возвращает запись как есть.

### 18.2 Цепочка и конфликт (§1)

На пару **запись + поле** может быть только ОДНА активная голова. Более
новая коррекция обязана нести `supersedesCorrectionId` текущей головы.
Молчаливый last-write-wins запрещён.

- Запись без ссылки, когда голова уже есть → отклонено (`stale`).
- Ссылка на уже заменённую коррекцию → отклонено (`stale`) — так ловится
  конкурентная запись, сделанная без учёта чужой коррекции (например,
  прилетевшей синком с другого устройства).
- Поля одного исправления обязаны иметь одну и ту же голову — иначе
  непонятно, что именно заменяется (`ambiguous`), и оформляется отдельно.
- **Две неподчинённые головы одного поля → `CORRECTION_CONFLICT`**:
  эффективным остаётся **ОРИГИНАЛ** (fail closed), «кто новее» по времени
  не выбирается. Новые исправления этого поля тоже отклоняются, пока
  конфликт не разрешён.

Порядок цепочки строится по ссылкам `supersedes`, а не по времени: время
ненадёжно при слиянии с другого устройства.

#### 18.2.1 Целостность цепочки: `INVALID_CORRECTION_CHAIN`

Слитые или повреждённые данные могут дать структуру, которую невозможно
прочитать однозначно. Чинить её «по времени» запрещено: `createdAt` при
слиянии с другого устройства ничего не доказывает. `corrFieldChains`
проверяет и **fail-closed** отклоняет поле, если найдено хотя бы одно:

| Поломка | Как определяется |
|---|---|
| цикл `A → B → A` | обход от головы к корню встречает уже виденный узел; либо у поля нет ни одного корня / ни одной головы |
| самозамещение `A → A` | `supersedesCorrectionId === id` |
| висячая ссылка | `supersedesCorrectionId` указывает на id, которого нет среди коррекций записи |
| дубль идентификатора | два узла с одинаковым `id` в цепочке одного поля |
| несвязанная ветка | обход от единственной головы не покрывает все узлы поля |

Последствие для поля: `heads = []`, `chain = []`, `invalid = [причины]`.
Дальше по всей цепочке потребителей:

- `proj` → эффективным остаётся **ОРИГИНАЛ**, поле перечислено в
  `_corrInvalid`; derived-движки исправленное значение не потребляют;
- `addCorrection` → отказ с `invalid: INVALID_CORRECTION_CHAIN` (дописывать
  поверх нечитаемой структуры нельзя);
- `corrHistory` → поле несёт `invalid`, история всех узлов остаётся видимой;
- инспектор → метка «История исправлений повреждена — показан оригинал» и
  явная причина; форма исправления по такому полю закрыта;
- Variant B → `corrBroken` = локальное изменение, тихое обновление из
  источника запрещено (`changed-conflict`).

**Две независимые первые коррекции — это НЕ поломка, а честный конфликт**
(две головы, §18.2). Ровно один корень не требуется: требуется, чтобы
корень и действующая версия вообще существовали. Иначе приложение назвало бы
нормальную конкурентную правку «повреждением данных».

**Легаси-формы с висячей ссылкой не существует.** В `DB.corrections` пишут
ровно два места — `addCorrection` и `extApplyUpdateToRecord` (override), и
оба с момента появления коллекции проставляют `supersedesCorrectionId`
явно. Отсутствие ссылки (`null`) — это корень, а не «легаси». Поэтому
висячая ссылка всегда означает повреждение.

### 18.3 Удалённый родитель (§2)

Коррекции **не** удаляются каскадом: они остаются историей и продолжают
синкаться и попадать в резервную копию. Пока родитель в tombstone:

- не участвуют в эффективной проекции;
- не потребляются derived-движками;
- обычный UI не считает их активными данными.

Отмена удаления автоматически возвращает цепочку в силу — проверка идёт
при чтении, отдельного действия не требуется.

### 18.4 Единый effective read layer (§6)

Все семантические потребители читают `projAll`/`proj`/`projOne`.
Переведены: серии (`calcStreak`, `calcBestStreak`, `calcConsistency`),
`resurface`, `livingLinks`, `rDiaryState`, `deriveAxes`, `stateScore`,
`rTrends`, `rHeatmap`, `correlations`, `smartInsights`, `periodReview`,
`rDig`, `rVector`, `weekContextForAI`, `dreamLifeContext`,
`buildAstroAiContext`, `smartNudge`, `buildGraph`, `crossLinks`,
`sphereLogsOf`, `reactToSphere`, `rPsyWorkspace`, `psyExpAnalysis` (N-of-1),
`mbPsychEvents` / `mbHealthEvents` / `mindBodyAssociations` (Mind–Body),
`rOverviewHealth`, `medsSectionHTML`, `medIntakeCountOnDay`, `rMedDetail`,
`rMedReminder`, `buildDoctorReport`, `cravingRisk`, `tipHelpCounts`,
`reactToCraving`, `rHealth`. Unified Intelligence (`unifiedEvents`) уже
читал через `projAll` и продолжает.

Подпись кэша «Живой карты» (`livingMapSig`) включает число коррекций —
иначе экран остался бы на старых значениях после исправления.

**Намеренно сырые чтения** помечены в коде комментарием
`raw intentionally` и допустимы только здесь: пути записи (`saveCI`,
`logSphere`, `deleteSphere`, `markHelped`, `saveLab`, `openLabAdd`,
`openDayCheckin`), писатели коррекций (`markWhyAction`, оригинал в
`openMoment`), чтение только идентификаторов (`psyFormSubmit`) и
проверка наличия записей (`rStreak`).

Производительность: `projAll` строит индекс коррекций один раз на вызов и
имеет быстрый выход, когда коррекций нет вовсе.

### 18.5 Взаимодействие с Variant B (§5)

**Активная коррекция по import-owned полю — это локальная правка
владельца.** Прежний детектор сравнивал сырые поля со снимком импорта и
коррекций не видел бы вовсе: они намеренно не трогают сырую запись.

Правило, доказуемо безопасное:

| Ситуация | Результат |
|---|---|
| replay ТОЙ ЖЕ версии источника | `existing`, коррекция жива |
| более новая ревизия меняет поле **с активной коррекцией** | `changed-conflict` |
| более новая ревизия меняет **только другие** поля | безопасный `changed`; коррекция сохранена |
| неразрешённый `CORRECTION_CONFLICT` на записи | `changed-conflict` (fail closed) |
| повреждённая цепочка (`_corrInvalid`) на записи | `changed-conflict` (fail closed) |

Пересечение множеств «поля, которые меняет источник» и «поля с активной
коррекцией» пусто ⇒ обновление не перезаписывает и не прячет ни одной
коррекции ⇒ применять безопасно. Иначе — fail closed, без угадывания.

**Override обязан разрешить коррекцию.** Иначе после «замены версией
источника» коррекция мгновенно снова легла бы поверх — замена была бы
ложью. Разрешение остаётся append-only: пишется коррекция-заместитель со
значением источника, `supersedesCorrectionId` прежней головы и честным
`origin: 'import_override'`. Прежняя правка владельца остаётся в истории.

**Keep-local** ничего в полях не трогает, поэтому активная коррекция
сохраняется автоматически.

`importHash` / `entityHash` / `sourceVersion` / провенанс исправлениями не
переписываются: правка владельца не выдаётся за версию источника.

### 18.6 Инспектор (§3, §4)

- Обычный вид показывает **эффективные** значения; исправленное поле
  помечено «Исправлено», поле с конфликтом показывает **оригинал** и
  честно называет причину.
- **История исправлений** — одна общая модель для всех типов (прежний
  частный случай «только моменты с зашитыми приятностью/энергией» удалён):
  оригинал, цепочка по порядку замен, отношение supersedes, активное
  значение, время и причина. Сырого JSON в обычном виде нет.
- **Технические данные** раскрывают отдельно: **A** оригинал записи,
  **B** цепочка исправлений, **C** эффективная запись.

### 18.7 Писатели исправлений (§7)

Кнопка «Исправить значение» доступна на всех correctable-типах. Форма
показывает текущее эффективное значение и оригинал, требует явного нового
значения, принимает необязательную причину и создаёт append-only событие.
Оригинал не мутируется никогда.

Доменная проверка (`REC_CORR` + `recCorrValidate`) по типу поля: диапазоны
(`checkins.sl` 0–24, оценки 0–10, `moments.valence/activation` 0–100),
перечисления (`medIntakes.status` taken/skipped, `cravings.outcome`
held/gave_in), даты (`ГГГГ-ММ-ДД`) и ISO-время, обязательность. Значение
вне контракта отклоняется — доказательное поле не угадывается.

#### 18.7.1 Снимок берётся в момент ПОКАЗА формы, а не сохранения

Контракт: снимок головы обязан представлять состояние, **которое видел
человек**. Снимок на момент сохранения этого не доказывает и открывает
дыру: человек видит V1 → синк с другого устройства приносит V2 → человек
сохраняет, глядя всё ещё на V1 → сохранение подхватывает V2 как «текущую
голову» и молча её замещает. Владелец перезаписал бы исправление, которого
никогда не видел.

Как сделано:

- `recCorrOpen` / `recCorrRender` при показе формы кладут в транзиентное
  состояние экрана типизированный **по каждому полю** снимок
  (`corrViewSnapshot`): `none` / `head` + id / `conflict` / `invalid`.
- Снимок берётся ОДИН раз на открытие формы (ключ `коллекция|id`) и
  переживает перерисовки — иначе перерисовка молча согласилась бы с чужой
  коррекцией.
- `recCorrSave` сверяет ТЕКУЩИЕ головы со снимком показа
  (`corrViewStale`). **Каждое** записываемое поле обязано совпасть со
  СВОИМ снимком; разные поля не схлопываются в одно общее ожидание.
- Любое расхождение → отказ: **ноль мутаций, ноль записи в хранилище**.
  Экран показывает, что данные изменились с момента открытия, и актуальные
  значения.
- Ожидание **не** обновляется автоматически. Обновить его может только
  явное действие человека — кнопка «Обновить и показать актуальное»
  (`recCorrReload`).

`corrHeadSnapshot` (снимок на момент сохранения) остался как вторая линия:
после прохождения сверки он по построению совпадает со снимком показа.

#### 18.7.2 Явная очистка nullable-значения (§3)

`psyObservations.valueNumber` объявлен `nullable`. Пустое поле ввода в
форме исправления означает «оставить как есть» — переинтерпретировать его
как `null` нельзя, иначе форма молча обнуляла бы поля, которых человек не
касался. Поэтому для nullable-полей есть **отдельное явное действие**
«нет числового значения (очистить)»:

- отметка → пишется коррекция с `patch = { valueNumber: null }`;
- эффективное значение становится `null`, **оригинал сохраняется** и
  остаётся видимым в истории;
- очистка уже пустого значения не создаёт исправления;
- отметка вместе с заполненным полем ввода — противоречие, отклоняется;
- у не-nullable полей действия очистки нет.

### 18.8 Что НЕ менялось

`SCHEMA_VERSION` (9). Миграции данных нет: старые коррекции без
`supersedesCorrectionId` остаются валидными — у поля с одной коррекцией
она и есть единственная голова. Оригинальные записи не переписываются.
