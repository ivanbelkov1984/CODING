## Детализация и последствия

### 1. «Записать» = центр-докнутый FAB
Круглая приподнятая кнопка «Записать» по центру над нижним таб-баром iPhone. Не занимает один из 4 слотов вкладок (вкладка = раздел, FAB = действие — семантика не смешивается). На iPad — кнопка «Записать» в группе «День» sidebar (+ FAB на узком iPad-portrait).
→ Обновляет `TARGET-INFORMATION-ARCHITECTURE.md §2–3`.

### 2. ＋ в topbar → «Записать»
Кнопка ＋ перестаёт молча означать «инсайт»; её `aria-label` меняется на «Записать», действие — открыть лист «Записать». Не удаляем (сохраняем привычную вторичную дверь, обнаруживаемость).
→ Обновляет `CURRENT-…` (факт-дефект остаётся описанием AS-IS) и `TARGET-…`, `UNIFIED-CAPTURE-CONTRACT §7`.

### 3. Отчёт врачу — поднять выше
Целевая доступность **≤2 действий** (было 4). Средства:
- карточка/шорткат «Отчёт врачу» в **Обзор → Здоровье-сводка**;
- пункт в быстром доступе (health summary) — прямой вход, не через «Ещё→Здоровье→внутрь».
Полная форма остаётся и в разделе Здоровья.
→ Обновляет `USER-FLOWS §8`, `TARGET-… §3 (Обзор)`.

### 4. Hash-роутинг — вводим (аддитивно)
Состояние экрана становится адресуемым: `#/today`, `#/diary/insights`, `#/astro/natal`, `#/capture/state` и т.п. Восстановление при перезагрузке; кнопка «назад» браузера/жест работает. **Canonical destination id остаются источником правды** — hash лишь отражает и восстанавливает их. Полностью обратная совместимость: без hash приложение работает как сейчас.
→ Отдельный под-этап в `NAVIGATION-MIGRATION-PLAN`; обновляет §4 «deep links».

### 5. iPad master-detail — да
Для широкого экрана (landscape/десктоп, ориентир ≥1024px) — двухпанельный режим: список слева, содержимое справа (например, список инсайтов | открытый инсайт). Внедряется **после** базового постоянного sidebar, отдельным этапом.
→ Обновляет `TARGET-… §5`; новый этап в migration plan.

### 6. Объединение Check-in + Момент → единый тип «Состояние» ⚠️ меняет модель данных
Владелец решил объединить два типа в один. Это **отменяет** прежнюю рекомендацию «оставить раздельными» и прежнее ограничение «не объединять evidence-типы» — но **только для пары Check-in/Момент** и **по явному решению владельца** (CLAUDE.md: изменения модели — через явное решение Ивана).

Проектное решение (безопасно, без потери данных):
- Пользователю — **один тип «Состояние»** с двумя режимами:
  - **быстро** — двухосевой снимок (приятность × энергия) + эмоция (бывший «Момент»), ≤15 сек;
  - **полно** — многоосевой суточный снимок (сон, ясность, стресс, мотивация, вещества, тон) (бывший «Check-in»).
- **Данные:** единая запись-суперсет с полем `mode: 'quick'|'full'`; исторические `checkins` и `moments` остаются **читаемыми** и сливаются в единую ленту «Состояние» через read-adapter (dual-read). Никакой деструктивной миграции; опциональный обратимый backfill — отдельным шагом.
- **Совместимость:** sync (`_u`, `__ts`, `_del`), backup roundtrip и чтение старых записей не ломаются.
- **Важно:** это изменение **storage/schema-модели** → **НЕ входит в navigation shell sprint**. Требует отдельного implementation-контракта с миграцией, back-compat, тестами и rollback (см. `NAVIGATION-MIGRATION-PLAN`, новый этап 2.x).

Прочие типы (Инсайт, Сон, «Зачем?», сфера, симптом, измерение, тяга, приём) **остаются раздельными** — объединение касается только Check-in и Момента.
→ Существенно обновляет `UNIFIED-CAPTURE-CONTRACT`.

### 7. Rollout флага и снятие drawer
Поэтапно, безопасно:
1. `arch_nav_v2` = **OFF** по умолчанию — сборка и приёмка (screenshot + a11y + маршрутная полнота + e2e 407/407).
2. После зелёной приёмки — **ON по умолчанию**; старый drawer остаётся как поведение при OFF (аварийный откат одним тумблером) на один стабилизационный цикл.
3. Если за цикл нет регрессий, о которых сообщил владелец, — **отдельный cleanup-PR** удаляет drawer и ветку OFF.
→ Обновляет `NAVIGATION-MIGRATION-PLAN §5, §1.4`.
