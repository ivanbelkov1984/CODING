# Архитектор жизни — Контракт единого ввода «Записать»

Статус: **DOCUMENTATION-ONLY / CONTRACT**. Проект единой точки ввода. **Не** сливает разные типы данных в одну неразличимую запись, **не** меняет storage/schema/sync/crypto, **не** пишет production-код.

Ключевой принцип: **«Записать» — это маршрутизатор входа, а не новая коллекция.** Он даёт одну дверь и общий каркас полей, но каждая запись по-прежнему сохраняется в свою существующую коллекцию своим существующим `save*`-обработчиком, со своим `kType`. Различия сущностей сохраняются полностью.

**Единственное исключение — по явному решению владельца (см. `OWNER-DECISIONS.md §6`):** типы **Check-in и Момент объединяются в один тип «Состояние»** (два режима — быстрый/полный). Это затрагивает модель данных, поэтому выполняется **отдельным implementation-контрактом** (не в navigation shell sprint) — с dual-read совместимостью, без потери данных и с rollback. Все остальные типы (Инсайт, Сон, «Зачем?», сфера, симптом, измерение, тяга, приём) остаются раздельными.

---

## 1. Что объединяется — и только на уровне входа

Сегодня 6–7 конкурирующих дверей (`ov-ci`, `ov-moment`, `ov-add`, `ov-why`, `ov-sphere-log`, `ov-craving`, `ov-drm`). Единый вход **[Записать]** предлагает выбор типа и открывает соответствующую **существующую** форму:

| Тип в меню «Записать» | Открывает (существующее) | Пишет в коллекцию | kType |
| --- | --- | --- | --- |
| **Состояние** (объединяет Check-in + Момент; режимы быстро/полно) | «Состояние» (единая форма; на переходном этапе — `ov-ci`/`ov-moment` под капотом) | единая «states» (канон) + dual-read из `checkins`/`moments` | `state_report` (наследует `self_report`; back-compat) |
| Мысль / Инсайт | `ov-add` (insight) | `insights` | — |
| Сон | `ov-drm` | `dreams` | — |
| «Зачем?» (разбор) | `ov-why` / `saveWhy` | `whys` | `process_reflection` |
| Запись сферы | `openSphereLog` / `saveSphereLog` | `sphereLogs` | — |
| Симптом | `ov-symptom` / `saveSymptom` | `symptoms` | `symptom_observation` |
| Измерение | `ov-measure` / `saveMeasure` | `measures` | `measurement` |
| Тяга / импульс | `ov-craving` / `saveCraving` | `cravings` | — |
| Приём лекарства (факт) | `logMedIntake` | `medIntakes` | `medication_intake` |

Объединяется **только точка входа и первичный выбор**. Данные, формы-финалисты, коллекции и kType остаются раздельными — **за единственным исключением Check-in + Момент → «Состояние»** (по решению владельца, §5a), которое выполняется отдельным schema-контрактом. Для остальных 8 типов это прямо соответствует ограничению «не объединять разные evidence-типы в одну неразличимую запись».

## 2. Как пользователь выбирает тип

Двухуровневый лист «Записать», сгруппированный по намерению (а не по коллекции):

- **Состояние сейчас** → **Состояние** (один пункт; внутри — быстро/полно)
- **Мысль и смысл** → Инсайт · «Зачем?» · Сон
- **Тело** → Симптом · Измерение · Приём лекарства · Тяга
- **Практики/цели** → Запись сферы

Правила выбора:
- **Состояние — один пункт** (объединение Check-in и Момента убирает прежнюю путаницу «что выбрать»). Различие теперь — не два типа, а два режима внутри одного: быстрый двухосевой снимок vs полный суточный.
- **Память последнего выбора и частоты**: последний использованный тип и 2–3 самых частых — вверху (быстрый ежедневный ввод < 30 сек).
- Контекстный дефолт: открытие «Записать» с экрана Здоровья предлагает телесные типы первыми (эвристика, не жёсткая).

## 3. Общий каркас полей (одинаков для всех)

Эти поля уже присутствуют/совместимы во всех коллекциях — «Записать» лишь единообразно их заполняет, ничего не добавляя в схему:

| Поле | Смысл | Уже есть в данных |
| --- | --- | --- |
| `createdAt` | момент создания (ISO) | да, во всех |
| `day` / `date` | привязка к дню | да |
| `note` | свободная заметка | да (в большинстве) |
| `_u` | метка обновления для синка | да |
| `sv` | версия схемы записи | да (`SCHEMA_VERSION`) |
| `privacyClass` | класс приватности (напр. `sensitive`) | да (здоровье/астро) |
| `id` | идентификатор | да |

Общий каркас = «когда/какой день/заметка/метки синка». Всё остальное — специализированное.

## 4. Что остаётся строго специализированным (не трогаем)

Специфичные поля каждого типа сохраняются как есть; «Записать» их не унифицирует:

- **Состояние** (суперсет, режим определяет заполняемое подмножество):
  - режим *быстро* (бывший Момент): `valence, activation, emo`;
  - режим *полно* (бывший Check-in): `sl, sq, cl, st, mv, nic, caf, alc, sugar, act, tone, emo`;
  - маркер режима: `mode: 'quick'|'full'`. Оба режима — один тип «Состояние», см. §5a.
- **Инсайт**: `title, body, tag, links[[…]]`.
- **Сон**: `title, text, symbols, tone`.
- **«Зачем?»**: `symptom, function, gain, need, cost, alternative, action, actionDone`.
- **Запись сферы**: `sphereId, value` (тип значения зависит от трекера: habit/counter/score/goal).
- **Симптом**: `name, severity`. **Измерение**: `name, value, unit`.
- **Тяга**: `kind, intensity, trigger, outcome`.
- **Приём**: `medId, status`.

## 5. Быстрый и расширенный режимы

- **Быстрый режим** (по умолчанию): минимальный набор полей типа + сохранение. Для Check-in — помнит последние выбранные факторы; цель ≤ 30 сек. Для Момента — только два слайдера + эмоция. Для симптома — имя + тяжесть.
- **Расширенный режим** (тап «Подробнее»): раскрывает все специализированные поля (заметка, вещества, символы сна, полный разбор «Зачем» и т.д.).
- Переход быстрый↔расширенный — внутри одной открытой формы (progressive disclosure), без потери введённого.
- Быстрый режим никогда не «съедает» данные: не показанные поля берут значения по умолчанию своей формы (как сейчас в `saveCI`/`saveMoment`).

## 5a. Объединение Check-in + Момент → тип «Состояние» (модель данных)

По решению владельца (`OWNER-DECISIONS.md §6`) два типа становятся одним. Это единственная унификация, затрагивающая данные, поэтому — отдельный контракт (не navigation shell).

**Целевая запись «Состояние»** — суперсет обоих: общий каркас (`createdAt, day, note, _u, sv, id, privacyClass`) + `mode:'quick'|'full'` + поля соответствующего режима. `kType: 'state_report'` (для новых записей).

**Безопасная миграция (обязательные свойства):**
- **Канон вперёд:** новые «Состояния» пишутся в единую коллекцию (`states`), либо, как компромисс back-compat, в существующую `checkins`, помеченную `mode`. Финальный выбор канона — в implementation-контракте.
- **Dual-read:** единая лента «Состояние» читает и `checkins`, и `moments` (историю) через adapter; ни одна старая запись не теряется и не переписывается.
- **Обратимость:** опциональный backfill исторических `moments` в канон — отдельный, идемпотентный и обратимый шаг; исходные коллекции не удаляются до подтверждённой стабилизации.
- **Sync/backup:** формат слияния (`_u, __ts, _del`) и backup roundtrip не ломаются; старые клиенты продолжают читать свои коллекции.
- **Rollback:** отключение унификации возвращает раздельное чтение без потери данных.

Пока контракт не выполнен, «Состояние» может работать как UI-обёртка над `ov-ci`/`ov-moment` (объединён вход и выбор режима), а разделение данных сохраняется — это промежуточно совместимо и не блокирует navigation shell.

## 6. Совместимость со storage и sync (жёсткое требование)

- **Ноль изменений схемы и коллекций.** Все 21 коллекция и их формат неизменны. «Записать» вызывает существующие `save*`-функции, которые уже пишут корректные `kType`, `sv`, `_u`, `privacyClass`.
- **Sync не затрагивается**: записи создаются теми же путями, что и сейчас → те же поля слияния (`_u`, `__ts`, `_del`-надгробия). Диспетчер не участвует в персистентности — только открывает форму.
- **Обратная совместимость чтения**: старые записи без новых UI-полей читаются как раньше (поля каркаса опциональны, как в текущем коде: напр. `v.tone || '—'`).
- **Undo/удаление**: без изменений (тот же `delUndo` + надгробия).

## 7. Какие существующие формы остаются внутри своих разделов

«Записать» — дополнительная дверь, а не замена. Все текущие входы сохраняются:
- Сферы: «Отметить»/«+добавить» на карточке (`openSphereLog`) — остаётся.
- Здоровье: план лекарства (`ov-med-add`), симптом, измерение, тяга, отчёт врачу — остаются в разделе.
- Разум/Дневник: добавление инсайта из раздела — остаётся.
- Today: быстрые действия (Check-in/Момент/Инсайт/Сон) — остаются (их состав/облегчение — задача Today v2, не здесь).
- ＋ в topbar перестаёт молча означать «инсайт» и **перенаправляется на «Записать»** (`aria-label` → «Записать»); не удаляется — сохраняется как вторичная привычная дверь (`OWNER-DECISIONS.md §2`).

## 8. Границы контракта
- НЕ создаёт единую неразличимую «captures»-запись для всех типов: 8 из 10 типов остаются раздельными коллекциями/kType.
- Диспетчер «Записать» (маршрутизатор входа) НЕ меняет `kType`, `SCHEMA_VERSION`, формат синка, крипто-границу.
- Объединение **только Check-in + Момент** → «Состояние» — по явному решению владельца; затрагивает модель данных и выполняется **отдельным контрактом** с миграцией/rollback (§5a), НЕ в navigation shell.
- НЕ реализует Today v2 и не меняет тексты интерпретаций.

## 9. Acceptance для будущей реализации (когда дойдёт до кода)
- Каждый тип создаётся через «Записать» ≤ 2 действий и сохраняется в **правильную** коллекцию с **правильным** kType (регрессионный тест на каждый тип).
- Существующие внутрисекционные формы продолжают работать (e2e без изменений).
- Backup roundtrip (data-only и complete) неизменен после создания записей через «Записать» — включая записи «Состояние».
- Быстрый режим «Состояние» ≤ 30 сек по числу обязательных полей.
- «Состояние» — один пункт с режимами быстро/полно; исторические Check-in и Момент видны в единой ленте (dual-read) без потери данных.
- Для контракта унификации (§5a): тест «ни одна старая запись `moments`/`checkins` не потеряна»; тест обратимости backfill; тест rollback.
