# DRIVE SYNC HUB v1 — read-only архитектурный аудит

**База:** MAIN `8af42ee` (после merge PR #177).
**Статус:** только аудит. Production-код не изменён, canonical-семантика не тронута.
**Область:** что Drive Sync Hub может переиспользовать, что обязан НЕ обходить,
и какие решения действительно требуют владельца.
**Решения владельца D-1…D-6 приняты** и зафиксированы в §10 — они являются
контрактом реализации v1. §9 сохранён как исходная постановка вопросов.

Каждое утверждение ниже проверено чтением реального кода и помечено ссылкой
`app.js:строка`. Там, где это вывод, а не факт кода, стоит явная пометка
**[вывод]**. Приватных данных владельца в документе нет — только имена функций,
константы и структура.

## 1. Текущий путь приёма внешних данных

Мост Final A задуман **provider-neutral** и уже описывает Drive как будущий
канал (`app.js:14936`–`14968`):

> «Google Drive / ChatGPT-экспорт / файл / внешний коннектор — ТОЛЬКО каналы
> приёма (adapters) одного универсального моста… Прямой Google Drive
> OAuth-адаптер — OPTIONAL/FUTURE и может быть добавлен поверх этого моста
> без изменения canonical-модели.»

Полный конвейер:

```
источник → канал (adapter.read) → normalize → canonical feed
        → validate → plan (preview, ноль мутаций)
        → owner confirm → атомарный commit → canonical коллекции
        → ledger + checkpoint
```

| Стадия | Функция | Файл |
|---|---|---|
| read | `EXT_CHANNEL_ADAPTERS[kind].read` — сейчас у ВСЕХ каналов `'owner_mediated'` | `app.js:14997` |
| normalize | `extChannelNormalize` → `extBridgeParseFeed` | `app.js:15002`, `15090` |
| validate | `extValidatePackage` | `app.js:15727` |
| plan | `extBuildPlan` (+ `extClassifyExisting`) | `app.js:17173`, `16976` |
| commit | `extCommitPlan` | `app.js:17450` |
| оркестрация | `extBridgeRefresh` / `extBridgeApply` | `app.js:15116`, `15203` |

**Ключевой факт:** ядро моста от канала НЕ зависит. Канал поставляет только
`read`; `normalize`, `importer` и canonical-контракты общие
(`app.js:14993`).

## 2. Модель источника/подключения

`externalConnections`, форма записи — `extConnNewRec` (`app.js:15026`):

```
{ id, label, kind, status, privacyClass:'sensitive',
  checkpoint: { committedPackageHashes: [], lastRefreshAt, lastError },
  stats: { refreshes, packagesCommitted, recordsCreated },
  container: null,          // provenance-контейнер (файл/архив), НЕ идентичность
  sourceStatusNote: null,
  createdAt, day, sv, _u }
```

`kind` ∈ `EXT_CHANNEL_KINDS` (`app.js:14972`) — **`google_drive_export` уже
существует**: `'manual_file' | 'chatgpt_export' | 'google_drive_export' |
'external_connector' | 'other'`.

`status` ∈ `EXT_SOURCE_STATUSES` (`app.js:14984`): `ready`, `refreshing`,
`preview_ready`, `source_unavailable`, `error_requires_user`, `disconnected`.
Комментарий кода прямо фиксирует, что слово «подключён» **не используется**,
потому что постоянного авторизованного соединения нет (`app.js:14980`).
Drive Sync Hub с OAuth это утверждение меняет — см. §9, решение D-1.

Жизненный цикл: `extConnCreate` / `extConnUpdate` (снимок + откат при сбое
persist) / `extConnDisconnect` / `extConnMarkUnavailable` / `extConnResume` /
`extConnForget` (`app.js:15040`–`15085`).

Два инварианта, которые Drive обязан сохранить:

- **`extConnDisconnect`** останавливает приём, но **все импортированные
  canonical записи остаются** — «это данные пользователя, а не кэш источника»
  (`app.js:15062`).
- **`extConnForget`** удаляет только состояние подключения. Canonical записи не
  трогаются; повторный импорт после forget безопасен через ledger
  (`app.js:15075`).
- Исчезновение объекта в источнике **никогда** не удаляет canonical запись
  (`app.js:14963`).

## 3. Canonical transaction path

`extBridgeApply` (`app.js:15203`) — это и есть та транзакция, которую Drive
обязан использовать, а не обходить:

1. **Терминальный гейт до любой работы.** Подача применяется, ТОЛЬКО если все
   элементы терминальны. Блокируют: `update-rejected`, `changed-conflict`,
   `stale-source-version`, `order-unknown`, `source-version-conflict`,
   `normalization-change` (`app.js:15218`). При блокировке canonical,
   журнал и чекпойнт не меняются ни на байт.
2. **Кандидат = клон DB.** Живая `DB` не мутируется вовсе до финального swap
   (`app.js:15234`).
3. **Пакеты коммитятся в одного кандидата**, сбой любого — кандидат отброшен
   целиком, откат byte-identical (`app.js:15275`).
4. **Один swap + один `persist()`** (`app.js:15292`).
5. **Чекпойнт двигается ровно один раз** — после успеха всего feed
   (`app.js:15304`).
6. **Degraded-состояние честное:** canonical применён, чекпойнт не сохранился →
   это НЕ full success; повтор безопасен через ledger (`app.js:15315`).

Идентичность записи — **семантический `sourceId`**; канал и контейнер (id файла
Drive, имя архива) — только provenance и идентичность подменить не могут
(`app.js:14949`, `15006`).

## 4. Checkpoint / revision семантика

**Два независимых слоя защиты от дублей:**

| Слой | Где | Свойство |
|---|---|---|
| `checkpoint.committedPackageHashes` | `app.js:15026`, `15304` | **ограничен** `EXT_CONN_MAX_HASHES = 200` (`app.js:14990`) — это оптимизация, не гарантия |
| Ledger `externalWorkSessions[].contentHash` | `app.js:15155`, `17555`, `17684` | **неограничен**, и именно он назван «страховкой от дублей» (`app.js:14990`) |

Хеш пакета покрывает `format/source/session/entities/links`
(`app.js:15150`), поэтому изменённая версия пакета никогда не совпадёт со
старым hash и построит полный план.

**Revision ordering (§19):** `extNormalizeSourceVersion` / `extCompareSourceVersions`
/ `extKnownHistoricalHashes` (`app.js:15623`, `15637`, `15656`). Если порядок
версий недоказуем — `order-unknown`, fail closed, автоприменение запрещено
(`app.js:17144`).

**Планы всех пакетов строятся последовательно на ОДНОМ кандидате**, чтобы
`sourceId`, впервые встреченный в двух пакетах одной подачи, не создал дубль
(`app.js:15137`).

## 5. Инкрементальное состояние синка: чего сейчас НЕТ

Текущий чекпойнт отвечает на вопрос «какие **пакеты** уже приняты». Он **не**
отвечает на вопросы, которые нужны непрерывному Drive-синку:

| Нужно Drive Hub | Есть сейчас | Разрыв |
|---|---|---|
| какие файлы наблюдаем | `container` — один, только provenance (`app.js:15008`) | нет списка наблюдаемых объектов |
| что изменилось с прошлого раза | `lastRefreshAt` (метка времени) | нет курсора изменений (Drive `startPageToken` / `changes.list`) |
| версия конкретного файла | `sourceVersion` на **записи** (`app.js:15623`) | нет per-file `modifiedTime`/`version`/`md5Checksum` |
| постраничный обход | — | нет |

**[вывод]** Drive Sync Hub v1 требует нового состояния уровня «наблюдаемый
объект источника» (fileId → последняя увиденная версия + курсор). Это
**дополнение к** `externalConnections`, а не замена checkpoint/ledger: оба
существующих слоя обязаны остаться, потому что именно они дают идемпотентность.

**Критично (риск, найденный в аудите):** `externalConnections` **входит в
`IDCOLS`** (`app.js:10990`) и, значит, синхронизируется между устройствами
через `mergeById` с правилом «побеждает больший `_u`» (`app.js:11023`). Два
устройства, одновременно ведущие один и тот же Drive-источник, могут затереть
чекпойнт друг друга по LWW. Сегодня это безопасно, потому что чекпойнт — лишь
оптимизация, а гарантия — ledger (`externalWorkSessions` тоже в `IDCOLS`,
объединяется по id). **Любой per-file курсор Drive обязан наследовать это же
свойство: быть оптимизацией, а не единственной гарантией.** Курсор, потерянный
или перезаписанный LWW, должен приводить максимум к лишней работе, никогда — к
пропуску или дублю.

## 6. Что Drive Sync Hub может переиспользовать без изменений

- Весь конвейер §1 целиком, включая preview, claim safety, дедуп, транзакцию.
- `kind: 'google_drive_export'` уже в enum (`app.js:14972`) — новая сущность не нужна.
- `container = { kind, id, label }` (`app.js:15008`) — ровно то место, где живёт
  `fileId` Drive: **provenance, не идентичность**.
- Все состояния источника (`app.js:14984`), включая `source_unavailable` —
  корректно описывает «доступ к файлу отозван».
- Ledger, чекпойнт, revision ordering, terminal-гейт, degraded-состояние.
- Backup/restore и E2EE-синк: `externalConnections` и `externalWorkSessions` уже
  в `IDCOLS` (`app.js:10990`) и переносятся копией.
- UI: экран источников `extRenderConnections` (`app.js:15492`) и трёхшаговый
  поток (`extSetStep`) — Drive становится ещё одним источником в том же списке.

**Иными словами: Drive Hub — это новый `read`, а не новый протокол записи.**

## 7. Что Drive Sync Hub НЕ имеет права обходить

| Запрет | Почему |
|---|---|
| Прямая запись Drive → `DB` мимо `extBuildPlan` / `extCommitPlan` | обходит provenance, дедуп, claim safety и атомарность |
| Собственный дедуп вместо ledger | ledger — единственная неограниченная гарантия (`app.js:14990`) |
| Автоприменение без owner confirm | подтверждение обязательно перед любой мутацией canonical (`app.js:15420`) |
| Идентичность по `fileId` | идентичность — только семантический `sourceId` (`app.js:14949`) |
| Удаление canonical при исчезновении файла | «только действие пользователя удаляет данные» (`app.js:14963`) |
| Продвижение чекпойнта до успешного commit | `app.js:15304` |
| Автоприменение при `changed-conflict` / `update-rejected` / `order-unknown` | terminal-гейт (`app.js:15218`) |
| Повышение claim-класса до факта | `EXT_FACTUAL_CLAIMS`, `app.js:15569`, `15776` |
| Сеть/AI внутри импорта | «Импорт строго локальный: без сети, без AI, без Google OAuth/Drive API» (`app.js:15537`) — **эта строка перестаёт быть верной с Drive OAuth и обязана быть переписана осознанно, а не молча** |

## 8. Приватность и безопасность

**Что есть сегодня:**

- Учётных данных провайдеров приложение **не хранит и не запрашивает**
  (`app.js:14964`).
- Backend — «тупое» E2EE-хранилище: таблица `spaces` с `db JSONB` / `cfg JSONB`
  (`backend/server.js:30`), endpoints только `GET/POST/PUT/DELETE
  /api/space` (`backend/server.js:84`–`153`). **Серверных исходящих запросов к
  внешним провайдерам нет вовсе.**
- CORS заперт на доверенные origin (`backend/server.js:52`).
- При включённой парольной фразе на сервер уходит только шифроблок
  (`packPayload`, `app.js:11054`); ключ на сервер не уходит.
- Device-local поля CFG (`apiUrl`, `spaceKey`, `lastSync`) **не** входят в
  переносимую копию (`backup/backup-adapter.mjs:41`).
- `externalConnections` и `externalWorkSessions` несут `privacyClass:'sensitive'`
  (`app.js:15033`, `17697`).
- Ledger хранит только аудит: ссылки, имена полей, хеши — **никаких полных
  transcript и дублей canonical-текстов** (`app.js:17674`).

**Новые границы, которые вводит Drive OAuth [вывод]:**

1. **Где живёт токен.** Сервера, способного держать refresh-token, нет
   (`backend/server.js` — только blob-store). Значит токен либо остаётся в
   браузере, либо появляется новый серверный компонент. Первое кладёт секрет в
   `localStorage`/`IndexedDB` того же профиля, который синхронизируется —
   **токен нельзя класть в `DB`/`CFG`, иначе он уедет на backend и в резервную
   копию.** Ближайший существующий прецедент — `CONNECTION_FIELDS`
   (device-local, вне копии).
2. **Scope.** Минимально достаточный — `drive.file` (только объекты, явно
   выбранные владельцем через Picker), а не `drive.readonly` на весь диск.
3. **Egress.** Сегодня из браузера наружу ходят только backend и AI-провайдеры
   (`app.js:10845`, `11504`, `12190`). Drive добавляет googleapis.com —
   новый постоянный получатель трафика.
4. **Содержимое.** Файлы Drive могут быть медицинскими/психологическими —
   privacy-класс уже `sensitive`, но объём и автоматизм чтения меняются.

## 9. Решения, которые действительно требуются от владельца

Ниже — только те вопросы, где **нельзя** выбрать за владельца, потому что они
меняют смысл продукта или границу безопасности. Всё остальное укладывается в
уже утверждённые правила.

### D-1. Модель доступа: owner-mediated или OAuth?

- **(a) Owner-mediated (без изменения границ).** Владелец сам выкладывает
  подготовленный feed; Drive Hub добавляет только удобство (память о файле,
  напоминание, статус). Учётные данные по-прежнему не хранятся, строка
  «импорт строго локальный» остаётся верной.
- **(b) Прямой Drive OAuth.** Приложение читает файлы само. Это **меняет**
  зафиксированные в коде утверждения: «постоянного авторизованного соединения
  нет» (`app.js:14980`) и «без сети, без Google OAuth/Drive API»
  (`app.js:15537`).

Без ответа реализация невозможна: (a) и (b) — разные продукты.

### D-2. Если (b): где живёт токен?

Варианты: только память сессии (переавторизация каждый раз) · device-local
хранилище вне `DB`/`CFG`/копии · новый серверный компонент с refresh-token.
Третий вариант впервые даёт серверу доступ к незашифрованным данным владельца и
ломает текущую E2EE-модель — рекомендую его не выбирать.

### D-3. Автоматизм чтения

Может ли Hub читать Drive **без явного действия** (по расписанию/при открытии)?
Сегодня любой приём инициирует человек. Автоматическое чтение — новая
привычка приложения ходить в сеть за личными данными.

Подтверждение импорта остаётся обязательным в любом случае: автоматизм — только
про `read`+preview, не про commit.

### D-4. Область наблюдения

Одна папка · явный список файлов · весь диск. Влияет на требуемый OAuth scope и
на объём инкрементального состояния (§5).

### D-5. Судьба записей при потере доступа к файлу

Текущее правило — canonical не трогается, источник помечается
`source_unavailable`. Подтвердить, что оно распространяется и на Drive
(рекомендую да, менять не нужно).

### D-6. Не-JSON файлы

Drive-папка обычно содержит документы/PDF/изображения, а не готовый
`architect-external-work` feed. Кто превращает документ в пакет? Варианты:
только владелец вне приложения · детерминированный парсер в приложении ·
AI-извлечение. **Третий вариант вводит AI в путь импорта и напрямую
противоречит `app.js:15537`** — отдельное решение с отдельным контрактом.

## 10. РЕШЕНИЯ ВЛАДЕЛЬЦА (D-1…D-6) — ПРИНЯТЫ

Раздел §9 выше — это вопросы, поставленные аудитом. Ниже — **ответы владельца**.
Они являются контрактом реализации v1: всё, что им противоречит, реализовано
быть не может.

### D-1 — Модель доступа: **прямой Google Drive OAuth (УТВЕРЖДЕНО)**

Основание владельца: Hub обязан давать реальное чтение одобренных Drive-подач в
одну кнопку по действию владельца. Ручная передача feed вручную для задуманного
Hub недостаточна.

**Drive — ТОЛЬКО новый read-адаптер.** Инвариант остаётся дословно:

```
Drive read
→ extChannelNormalize
→ extBridgeParseFeed
→ extValidatePackage
→ extBuildPlan / preview
→ подтверждение владельца
→ extCommitPlan
→ ledger + checkpoint
```

Запрещено: прямой путь Drive → DB · новый дедуп · новая модель canonical-идентичности.

**Следствие для документации кода:** утверждения `app.js:14980` («постоянного
авторизованного соединения нет») и `app.js:15537` («импорт строго локальный: без
сети, без AI, без Google OAuth/Drive API») перестают быть верными и обязаны быть
переписаны осознанно в рамках реализации — молча оставлять их нельзя.

### D-2 — Хранение токена: **только память сессии**

Access-token в v1 живёт **исключительно в памяти сессии**.

Запрещено помещать токен в: `DB` · `CFG` · `localStorage` · постоянные
auth-хранилища `IndexedDB` · backend · E2EE-пакет синхронизации · зашифрованную
резервную копию · GitHub · логи.

Серверного компонента с refresh-token **нет**. Повторная авторизация после
перезапуска приложения или истечения токена в v1 приемлема.

**E2EE-архитектуру ослаблять ради удобства запрещено.**

### D-3 — Автоматизация: **только явный запуск владельцем**

Никакого фонового расписания · тихого чтения при старте · периодического
опроса · Drive-запросов из service worker.

Владелец явно нажимает «Синхронизировать». От этого действия допустимы
`read` + `normalize` + `preview`. **Canonical-commit по-прежнему требует
существующего явного подтверждения** — автоматизм касается только чтения.

### D-4 — Область наблюдения: **явный allowlist объектов**

Доступ ко всему диску не запрашивается **по продуктовому замыслу**, никогда.

v1: явный список объектов-подач, выбранных владельцем. Минимально достаточный
Google scope / модель Picker. UI может группировать выбранные подачи в
тематические каналы (Жизнь · Психология · Сны · Духовное · Отношения и т. д.).

Выбор одной выделенной папки `_ARCHITECT/FEEDS` допустим **как эргономический
слой только при доказательстве**, что он работает в той же минимальной границе
доступа.

**Тихая эскалация до drive-wide readonly запрещена.** Если Google API технически
вынуждает существенно более широкий scope для наблюдения за папкой —
**ОСТАНОВИТЬСЯ и предъявить точные доказательства** до изменения scope.

### D-5 — Исчезновение источника: **существующий инвариант подтверждён**

Потерянный / отозванный / удалённый Drive-источник → `source_unavailable` →
canonical записи **не трогаются**. Исчезновение источника **никогда** не является
удалением canonical данных.

### D-6 — Формат входа: **только детерминированные подготовленные подачи**

v1 принимает исключительно пакеты `architect-external-work` (JSON/feed) и уже
поддерживаемые мостом детерминированные обёртки пакетов.

Запрещено разбирать произвольные Google Docs · PDF · изображения · свободные
документы. **AI-извлечение не добавляется.** Извлечение из документов и AI —
отдельное более позднее решение по privacy и семантике.

## 11. Вывод после решений

Архитектурный вывод аудита подтверждён решениями: **Drive Sync Hub — это новый
`read` поверх неизменных `normalize → plan → confirm → commit → ledger`.**
Canonical-семантика не меняется.

Реализация v1 разблокирована и ведётся отдельной веткой от актуального `MAIN`.
Этот документ остаётся documentation-only артефактом и production-кода не несёт.

### Обязательное к проверке на этапе реализации

1. **D-4 — граница scope.** До написания OAuth-кода предъявить доказательство,
   какой минимальный Google scope достаточен для выбранных объектов и возможно
   ли наблюдение за папкой в той же границе. При вынужденном расширении —
   остановка и отчёт, а не тихая эскалация.
2. **D-2 — изоляция токена.** Доказывается тестами: токена нет в `DB`, `CFG`,
   `localStorage`, `IndexedDB`, теле запроса к backend, резервной копии,
   пакете синхронизации, логах и evidence.
3. **Курсор — только оптимизация.** Как показано в §5, `externalConnections`
   синхронизируется LWW. Потеря или перезапись per-file курсора обязана давать
   максимум лишние чтения и **никогда** — пропущенную canonical-работу.
   Единственная гарантия идемпотентности остаётся за ledger.
