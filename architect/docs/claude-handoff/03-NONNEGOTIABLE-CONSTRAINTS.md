# 03 — NONNEGOTIABLE CONSTRAINTS

## A. Сохранность данных

1. Никакая функция не имеет права молча удалять, переименовывать или пересобирать существующие пользовательские данные.
2. Любая миграция должна быть:
   - версионированной;
   - идемпотентной;
   - обратно совместимой;
   - протестированной на synthetic fixtures;
   - с явным rollback либо доказательством, почему reverse migration не нужна.
3. Реальные данные Ивана запрещено помещать в GitHub, CI, screenshots, fixtures или внешние тестовые сервисы.
4. Нельзя считать localStorage и IndexedDB одной транзакционной системой без отдельного компенсирующего протокола.

## B. Архитектура

1. Существующая vanilla-JS PWA остаётся продуктовым ядром.
2. Запрещена самовольная миграция на React/Next/TypeScript/Tailwind/shadcn или новую storage-библиотеку.
3. Нельзя создавать второе параллельное приложение.
4. Новые модули должны встраиваться через небольшие проверяемые seams/adapters, а не размножать копии production-логики.
5. Тесты обязаны использовать production-модуль либо тот же чистый core с dependency injection. Дублирование логики в fake Store не является доказательством.

## C. Privacy и безопасность

1. GitHub содержит только код и synthetic data.
2. Секреты подключения, API keys, sync passphrase, recovery material и локальные идентификаторы не входят в переносимый export.
3. При включённом E2EE сервер не должен получать открытый diary payload.
4. Нельзя обещать, что AI-провайдер не видит выбранный пользователем текст: провайдер видит ровно отправленный фрагмент.
5. Пароли резервных копий и sync passphrase не должны оставаться в UI после завершения/закрытия операции.
6. Криптография строится только на browser Web Crypto и известных параметрах; самодельные шифры запрещены.

## D. Медицинские границы

Без отдельного owner-approved regulatory contract запрещено:

- ставить диагноз;
- назначать или менять дозировку;
- утверждать безопасность сочетания препаратов;
- выдавать clinical alerts как медицинское решение;
- скрывать неопределённость источника.

Допустимы: структурирование данных, напоминания по явно заданному плану, подготовка вопросов врачу, хранение документов и отображение измерений.

## E. Психология

1. ИИ может формулировать гипотезы, но не выдавать их за установленную личность или намерение другого человека.
2. Нельзя усиливать зависимость пользователя от модели.
3. Нельзя подменять кризисную помощь литературным или мистическим объяснением.
4. Источники вывода должны быть видимы: запись, история, анкета, вычисление или AI hypothesis.

## F. Астрология и прогнозирование

1. Астрология хранится как отдельный интерпретационный домен.
2. Она не может служить причиной диагноза, риска, вероятности заболевания или утверждения о чужих намерениях.
3. Прогноз должен быть сценарным: условия, альтернативы, временной горизонт, неопределённость.
4. Расчётная часть и интерпретационная школа должны быть разделены.

## G. Git и процесс

1. `MAIN` — production baseline.
2. Никаких direct pushes в `MAIN`.
3. Никаких force-push.
4. Максимум одна активная implementation branch.
5. Каждая новая ветка начинается от подтверждённого актуального base.
6. После merge task-ветка удаляется.
7. PR должен содержать:
   - scope;
   - changed files;
   - risk;
   - tests actually run;
   - blocked tests;
   - rollback;
   - explicit non-goals.
8. «Тест не запущен» нельзя заменять словами «covered» или «expected pass».

## H. UX

1. Все критические операции доступны с iPhone/iPad через интерфейс.
2. Пользователь не должен переносить patch, bundle или выполнять terminal commands.
3. Разрушительные действия требуют ясного подтверждения.
4. Ошибки должны объяснять состояние и не скрывать частичный результат.
5. Offline/reload — обязательная проверка для storage, backup и service-worker изменений.
