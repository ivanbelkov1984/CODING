# DRIVE SYNC HUB v1 — контракт реализации

База: MAIN `8af42ee`. Решения владельца D-1…D-6 — см.
`DRIVE_SYNC_HUB_AUDIT.md` §10; этот документ описывает, **как именно** они
реализованы и чем доказаны.

---

## 1. Инвариант: Drive — только новый `read`

```
Drive read → extChannelNormalize → extBridgeParseFeed → extValidatePackage
→ extBuildPlan / preview → подтверждение владельца → extCommitPlan
→ ledger + checkpoint
```

Ни один шаг конвейера не изменён. Drive добавляет **только** источник текста
подачи. Практически это выражено так: `driveReadFeed` собирает изменившиеся
файлы в ОДИН feed `architect-external-work-feed-v1` и отдаёт его существующему
`extBridgeRefresh`, ровно как это делает архивная поставка (.zip).

| Запрет владельца | Как обеспечен |
|---|---|
| прямой путь Drive → DB | `driveReadFeed` не пишет в `DB` вовсе; единственный писатель — `extCommitPlan` |
| свой дедуп | его нет; гарантия — ledger `externalWorkSessions.contentHash` |
| своя модель идентичности | `sourceId` не трогается; `fileId` кладётся в `container` как происхождение |
| автоприменение | `driveSyncNow` доводит только до preview; commit — отдельное действие |

## 2. D-4: граница доступа и доказательства

Владелец потребовал доказать границу scope до написания OAuth-кода и
остановиться, если Google вынуждает расширение. Результат проверки:

| Scope | Категория Google | Что даёт |
|---|---|---|
| `drive.file` | **non-sensitive** | «Create new Drive files, or modify existing files, that you open with an app or that the user shares with an app while using the Google Picker API or the app's file picker» |
| `drive.readonly` | **restricted** | чтение всего диска |
| `drive.metadata.readonly` | **restricted** | метаданные всего диска |

Последствия restricted-скоупов по документации Google: «These scopes provide
wide access to Google user data and require restricted scope OAuth App
Verification», и дополнительно — «If you store restricted scope data on servers
(or transmit), then you must go through a security assessment». Google сам
рекомендует обратное движение: «If your Drive app uses restricted scopes, we
recommend migrating to a non-sensitive Drive API scope».

**Вывод по папке `_ARCHITECT/FEEDS`.** Владелец разрешил папку как
эргономический слой **только при доказательстве**, что она работает в той же
минимальной границе. Такого доказательства нет: документация Google нигде не
утверждает, что выбор папки в Picker распространяет `drive.file` на её
содержимое, а перечисление содержимого папки через `files.list` описано без
гарантии работы в границе `drive.file`.

Поэтому в v1 **папка не поддерживается**, и это НЕ является остановкой по
условию владельца: остановка требовалась при вынужденном расширении scope, а
расширения не происходит — реализован строго `drive.file` и явный allowlist
файлов. Возврат к вопросу возможен позже, если появится однозначное
подтверждение от Google.

Источники:
- https://developers.google.com/workspace/drive/api/guides/api-specific-auth
- https://developers.google.com/workspace/drive/picker/guides/overview

## 3. D-2: где живёт токен

`_driveTok` — переменная модуля. Больше нигде.

| Место | Токен |
|---|---|
| `DB` | нет |
| `CFG` | нет (там только **публичный** `driveClientId`) |
| `localStorage` | нет |
| `IndexedDB` | нет |
| тело запроса к backend / пакет синхронизации | нет |
| резервная копия (до и после шифрования) | нет |
| запись `externalConnections` | нет |
| логи, evidence, GitHub | нет |

Серверного refresh-token нет: backend (`backend/server.js`) — это E2EE
blob-store без исходящих запросов, и заводить в нём OAuth-компонент означало бы
дать серверу доступ к незашифрованным данным владельца. После перезапуска
приложения нужна повторная авторизация — осознанная цена за то, что секрет не
переживает сессию.

`driveClientId` в `CFG` — публичный идентификатор OAuth-клиента, он по природе
виден в любом браузерном OAuth-приложении и секретом не является.

## 4. D-3: что запускает чтение

Только явное действие: `driveSyncNow`. Ни расписания, ни чтения при старте, ни
опроса, ни обращений из service worker. Скрипты Google (`gsi/client`,
`apis.google.com/js/api.js`) грузятся **лениво**, из обработчика действия —
офлайн-first старт остаётся полностью локальным, и в разметке их нет.

`read + normalize + preview` идут от одного нажатия. **Canonical-commit
по-прежнему требует отдельного подтверждения** — существующий контракт моста не
ослаблен.

## 5. Инкрементальное состояние (курсор)

`externalConnections[].driveFeeds[] = { fileId, name, mimeType, cursor }`, где
`cursor = { modifiedTime, version, md5 }`.

**Курсор — исключительно оптимизация.** Совпал → файл не скачивается. Не
совпал или отсутствует → файл читается заново. Единственная гарантия
идемпотентности — ledger моста.

Это не стилистическое замечание, а следствие устройства синхронизации:
`externalConnections` входит в `IDCOLS` и сливается между устройствами по
правилу «побеждает больший `_u`». Курсор может быть затёрт чужим устройством —
и это обязано стоить максимум лишнего чтения.

Курсор двигается **только после успешного применения подачи** (там же, где
чекпойнт моста). Неудачный или отменённый импорт курсор не трогает.

## 6. D-5: исчезновение источника

Три пути исчезновения — и все ведут к одному:

| Событие | Поведение |
|---|---|
| файл удалён (404) | `missing`, источник → `source_unavailable` |
| доступ отозван (403) | то же |
| файл в корзине (`trashed: true`) | то же |

Canonical записи **не трогаются никогда**. Отключение источника
(`driveDisconnect`) гасит токен в памяти и останавливает приём, но
импортированные записи остаются: это данные владельца, а не кэш источника.

---

## 7. D-6: что принимается

Только `architect-external-work` v1/v2 и уже поддерживаемая мостом обёртка
feed. Разбор идёт существующим `extBridgeParseFeed` — своего формата у Drive
нет. Произвольный текст, Google Docs, PDF, изображения отклоняются с понятной
причиной. AI-извлечения нет.

---

## 8. Приватность: service worker

Найдено и закрыто в этой работе: `sw.js` кэшировал всё, кроме
`railway.app` / `api.anthropic.com`. Ответы `googleapis.com` — то есть **личное
содержимое подач владельца** — осели бы в кэше и пережили бы сессию, при том
что сам токен по D-2 живёт только в памяти. Теперь Google-хосты исключены из
кэширования явно, а собственные ассеты приложения кэшируются по-прежнему
(офлайн не сломан). Обе половины проверяются тестом.

## 9. Тесты

`tests/driveSyncHub.spec.mjs` — **52 / 0**. `tests/driveSyncHub-mutation.mjs` —
**11 / 0**.

Требования владельца по OAuth/безопасности:

| Требование | Сценарий |
|---|---|
| токен не в DB/CFG | «токена нет в DB и CFG» |
| токен не в localStorage/IndexedDB | два отдельных сценария, IndexedDB обходится целиком |
| токен не в теле запроса к backend | «токена нет в пакете синхронизации» |
| токен не в копии | до и после шифрования конверта |
| токен не в логах/evidence | privacy canary + отсутствие настоящих ключей в сборке |
| disconnect/revoke оставляет данные | «импортированные записи остаются» |
| истёкшая авторизация fail-closed | «отказ с просьбой переподключиться» |
| широкий доступ не запрашивается тихо | scope-сценарий + отсутствие restricted-скоупов в сборке |

Требования по Drive:

| Требование | Сценарий |
|---|---|
| первая подача → preview → commit | §2 сюиты |
| точный повтор → ноль дублей | курсор специально сброшен, чтобы доказать, что защита — ledger |
| изменённая ревизия → Variant B | конфликт распознан, применение заблокировано |
| конфликт → ноль частичного применения | правка владельца цела, дубля нет |
| два файла с одним sourceId → одна сущность | `fileId` идентичность не подменяет |
| отозванный/удалённый файл → `source_unavailable` | три пути (404 / 403 / корзина) |
| потеря курсора → сходимость | повторное чтение, ноль дублей |
| копия хранит метаданные, но не секрет | оба утверждения проверяются вместе |

**Две ложнозелёные проверки, найденные мутациями и исправленные усилением
тестов (не ослаблением мутантов):**

1. Путь «файл в корзине» не покрывался вовсе — мутант, удалявший canonical на
   этом пути, проходил сюиту насквозь. Добавлен сценарий с реальным поведением
   Drive (корзина отдаёт метаданные, а не ошибку).
2. Проверка «токена нет в записи подключения» не имела в подключении ни одной
   подачи, поэтому утечка токена в элемент allowlist была ей не видна.

## 10. Что НЕ сделано в v1 и почему

| Не сделано | Причина |
|---|---|
| наблюдение за папкой | граница `drive.file` для содержимого папки не доказана (§2) |
| фоновая синхронизация | запрещена D-3 |
| разбор документов / AI-извлечение | запрещено D-6, отдельное решение по privacy |
| серверный refresh-token | запрещён D-2, ломает E2EE-модель |
| UI выбора файлов на экране источников | ниже: требуется owner-настройка OAuth-клиента |

**Внешняя предпосылка, которую невозможно закрыть кодом:** нужен OAuth client id
из Google Cloud Console с разрешённым origin GitHub Pages. Пока `CFG.driveClientId`
пуст, `driveConnect` честно отказывает с понятным сообщением; вся остальная
логика работает и покрыта тестами через подменяемый транспорт `DRIVE_NET`.

## 11. Изменения контракта в коде

Утверждения, которые перестали быть верными с приходом D-1 и должны быть
переписаны в комментариях моста при следующем касании этого кода:

- `app.js:14980` — «постоянного авторизованного соединения с провайдером нет»;
- `app.js:15537` — «импорт строго локальный: без сети, без AI, без Google
  OAuth/Drive API».

Оба относятся к путям **до** Drive Sync Hub и остаются верными для них, но как
общее утверждение о приложении больше не годятся.

`SCHEMA_VERSION` = 9 без изменений. Миграции данных нет: `driveFeeds` —
дополнительное поле существующей записи `externalConnections`, старые записи
без него читаются как «подач не выбрано».
