## 2. Scalar merge contract

Список скаляров больше **не пишется руками**. Он выводится из `DEFAULT_DB`:

```
SCALAR_KEYS = ключи DEFAULT_DB − IDCOLS − DB_INTERNAL_KEYS
```

Рядом стоит `SCALAR_REGISTRY` — явный реестр «я знаю, что это скаляр и как он
синхронизируется». Тест сверяет три множества и падает, если:

- ключ `DEFAULT_DB` не отнесён ни к коллекциям, ни к скалярам, ни к внутренним;
- скаляр не зарегистрирован в `SCALAR_REGISTRY`;
- в реестре остался ключ, которого уже нет.

Именно это и не давало заметить D-1: поле добавляли в `DEFAULT_DB`, а в
sync-контракт — нет, и ничто не возражало.

**Семантика не менялась:** та же scalar-LWW «побеждает документ с большим
`__ts`». ID-коллекции не тронуты.

## 3. Storage durability

Добавлены `storagePersisted()`, `requestPersistentStorage()`,
`storageEstimate()`, `storageSummary()`.

- Разрешение **не запрашивается навязчиво**: только по явному нажатию на экране
  «Хранилище и диагностика».
- Показываются: занято / доступно / процент, статус постоянного хранилища,
  размер данных профиля, число медиа-файлов, состояние последней записи.
- **Абсолютной защиты не обещаем.** Текст в UI прямо говорит: постоянное
  хранилище снижает риск очистки, но ОС всё равно вправе освободить место, и
  основной защитой остаётся резервная копия.
- Если API недоступен (старый WebKit) — все поля `null`, приложение работает,
  ничего не падает. Проверено тестом с подменённым `navigator.storage`.
- **Байты медиа не суммируются чтением блобов.** Считается только количество
  ключей (`idbKeys`), общий объём берётся из `estimate()`. Иначе строчка в UI
  тянула бы весь медиа-архив в память. Проверено тестом: `idbGet` в этом пути
  не вызывается.

## 4. Quota-safe writes — транзакция над набором ключей

> Owner review #2 (PR #159). Первая версия была **не транзакционна**:
> последовательность `DB → CFG → backup` без отката. Если `CFG` падал по квоте,
> повтор переписывал только `DB`, и функция возвращала `true` — пользователь
> получал ложный успех и терял изменение настроек. Сбой резервного слота
> попадал в общий `catch` и мог скрыть уже частичное состояние.

Запись — **транзакция над набором ключей**, которые операция объявляет
сохранёнными (`arch5_db_*`, `arch5_cfg_*` и, при непустых данных, `arch5_bak_*`):

1. Перед записью снимается прежнее значение каждого ключа.
2. Набор пишется целиком.
3. При **любой** ошибке уже изменённые ключи откатываются к снятым значениям в
   обратном порядке, функция возвращает `false`.
4. Повтор после освобождения места повторяет **весь набор**, а не только `DB`.
5. Частичный успех не существует как исход: `true` возвращается, только когда
   записаны все ключи.
6. `QuotaExceededError` распознаётся (включая `code 22` / `1014` и
   `NS_ERROR_DOM_QUOTA_REACHED`); место освобождается **только за счёт старых
   ежедневных снимков**, пользовательские записи не удаляются никогда,
   `localStorage.clear()` не вызывается.
7. `persistLocal()` не пишет в `localStorage` напрямую — только через
   транзакционный помощник. Это проверяется тестом по исходнику функции.

### Сбой отката = критическое состояние (финальный проход)

> Owner review: первая версия `_txWrite` глотала исключения отката пустым
> `catch` — при неудачном rollback хранилище оставалось смешанным, а вызывающий
> код продолжал prune/retry, как будто состояние известно.

- Snapshot прежних значений снимается **до первой записи**; если `getItem`
  любого ключа сам падает — транзакция не начинается вовсе.
- Откат каждого изменённого ключа выполняется с **read-back проверкой**:
  значение после отката обязано побайтно совпасть со снятым.
- Результат несёт `rollbackAttempted`, `rollbackFailed`, `rollbackErrors`
  (имена ключей) и `affectedKeys`.
- `rollbackFailed` переводит профиль в **критическую блокировку**
  `transaction-rollback-failed`: обычные persist запрещены, синк запрещён,
  prune/retry запрещён. Пользователь видит: «Не удалось гарантированно
  восстановить прежнее состояние хранилища. Запись и синхронизация остановлены
  до восстановления». Диагностика показывает имена затронутых ключей — без
  содержимого значений.
- Retry после освобождения места допустим **только** если откат первой попытки
  полностью успешен (состояние известно и прежнее).
- Критическую блокировку `hydrate()` не снимает — только явное разрешение
  пользователя (restore / export / confirmed reset).

## 5. Startup integrity и recovery write lock

> Owner review #3 (PR #159). Первая версия показывала toast, но **не блокировала
> последующую запись**: первое же действие пользователя вызывало `persist()` и
> перезаписывало повреждённый слот, уничтожая возможность ручного спасения.
> Хуже того, `migrateRecords()` мутировал живой `DB` по ходу и мог бросить на
> середине — полурезультат оставался в памяти и закреплялся следующим `persist`.

- **Миграция выполняется над клоном.** `hydrate()` передаёт
  `JSON.parse(JSON.stringify(DB))` в `migrateRecordsOn(draft)` и коммитит
  результат в `DB` **только после полного успеха**. Исключение на середине
  откатывает всё к домиграционному состоянию.
- **Recovery write lock** — профиль-специфичная блокировка. Взводится, когда
  слот повреждён без резервной копии (`profile-corrupt`) или упала миграция
  (`migration-failed`). Пока она стоит, `persistLocal()` для этого профиля
  возвращает `false` и **не пишет ничего**; причина видна в
  `lastPersistError().locked`. Другие профили не затронуты.
- Снять блокировку можно **только** одним из трёх явных исходов:
  `restored` (восстановление из резервной копии), `exported` (сырой слот
  выгружен как есть — `exportRawSlot()` отдаёт содержимое **до** любой
  перезаписи), `discarded` (осознанный сброс, требует подтверждения:
  `discardCorruptProfile(false)` не делает ничего). Произвольная строка
  блокировку не снимает.
- Повреждённый JSON профиля остаётся в хранилище **byte-identical** — проверено
  тестом, который кладёт обрезанный JSON, делает обычную правку и требует
  посимвольного совпадения сохранённой строки.
- Недоступный `localStorage` (D-6) больше не роняет старт: миграция старых
  ключей стала best-effort, приложение открывается на дефолтах.
- UI: панель на экране «Хранилище и диагностика» объясняет, что запись
  заблокирована и почему, и предлагает ровно эти три действия настоящими
  кнопками.

### Финальный проход: полный write barrier и per-profile реестр

> Owner review: блокировка останавливала только `persistLocal()`. `persist()`
> двигал метки времени и планировал синк; `runSync()`/`applyServer()` могли
> слить серверные данные в runtime и отправить PUT; `snapshotDaily()` писал
> снимок; `restoreSnapshot()`/`discardCorruptProfile()` показывали успех до
> проверки записи; сама блокировка была одной глобальной переменной и исчезала
> при `hydrate()` другого профиля.

- **Реестр per-profile:** `Map profileId → { reasons, critical, affectedKeys }`.
  `hydrate()` трогает только запись СВОЕГО профиля. Сценарий «A повреждён →
  работа в B → возврат в A» проверен: A остаётся заблокирован, его слот
  byte-identical, B при этом полноценно пишется.
- **`persist()` под блокировкой:** не меняет `DB.__ts`/`CFG._ts`, не пишет, не
  планирует синк, возвращает `false`. При неудачной записи метки времени
  откатываются и синк не планируется — на сервер не может уехать состояние,
  которого нет локально.
- **Sync fail-closed:** `scheduleSync`, `runSync`, `applyServer`, `pullData`,
  `recoverFromKey` отказывают под блокировкой: ни pull, ни merge в runtime, ни
  PUT/POST, ни обновления `lastSync`. Статус в UI: «Синхронизация
  приостановлена: режим восстановления». Тест: настроенный синк с согласием и
  ключом пространства даёт **ноль** сетевых вызовов под блокировкой.
- **Снимки:** `snapshotDaily()` под блокировкой не создаёт ключей — runtime
  может содержать `DEFAULT_DB` вместо реальных данных.
- **Транзакционное разрешение:** `commitRecoveredState()` пишет кандидата в
  `db/cfg/bak` при ЕЩЁ стоящей блокировке; только успешная запись коммитит
  runtime и снимает её. `restoreSnapshot()` идёт этим путём (исход `restored`
  реально работает); `discardCorruptProfile()` возвращает фактический
  успех/сбой, `recoveryDiscard()` показывает ошибку при сбое, а не ложное
  «сброшено»; `recoveryExportRaw()` снимает блокировку только после реально
  инициированной выгрузки. Восстановление зашифрованной копии активируется
  через `hydrate()` заново прочитанного здорового слота — обычная блокировка
  снимается фактом успешной активации, критическая требует явного разрешения.

## 6. Deploy recovery

> Owner review #1 (PR #159). Первая версия **не обеспечивала заявленного
> восстановления**. На первом обновлении после внедрения Волны 5 кэша `arch-lkg`
> ещё не существует, а `activate` удалял все versioned-кэши кроме `V` и `LKG` —
> предыдущая рабочая сборка исчезала до того, как новая подтвердит старт. Кроме
> того, `LKG` нигде не использовался для выдачи: навигация делала
> `caches.match('./index.html')` и могла вернуть текущий сломанный `V`, а message
> handler умел только `startup-ok` и `version?`.

Честная оценка среды: **полностью автоматический откат на GitHub Pages
невозможен** — сервер всегда отдаёт свежий `index.html`. Реализовано то, что
реально работает, и это проверено сценарно:

1. **Seed LKG до уборки.** `activateWithRecovery()` сначала проверяет, есть ли
   `LKG`. Если нет — предыдущий versioned-кэш назначается last-known-good (он
   рабочий по построению: пользователь на нём работал), и только потом
   выполняется удаление старых кэшей. Это закрывает дыру первого обновления.
2. **Health marker.** Приложение отправляет `arch:startup-ok` через 8 секунд и
   только если не было `error`/`unhandledrejection`. Лишь после этого текущая
   сборка копируется в `LKG`.
3. **Реальная выдача.** Режим восстановления хранится флагом в `LKG`. Пока он
   включён, и навигация, и ассеты обслуживаются **из `LKG`**, а не из текущего
   `V` — иначе «выдача по запросу восстановления» осталась бы заявлением.
4. **Message API:** `arch:restore-lkg` (включить восстановление),
   `arch:exit-recovery` (вернуться к текущей версии), `arch:version?`
   (текущая версия, last-known-good, состояние режима).
5. **Петли нет по построению:** service worker не перезагружает ничего сам;
   `location.reload()` вызывает приложение по явному действию пользователя.
   Успешный старт автоматически снимает режим восстановления.
6. **Данные пользователя не затрагиваются** — восстановление касается только
   ассетов; service worker не обращается к `localStorage`/IndexedDB (проверено).

### Финальный проход: build identity, fail-closed, ACK, bootstrap

> Owner review: `handleMessage` игнорировал `msg.build` — рабочая B, выданная
> из LKG в режиме восстановления, через 8 секунд слала свой health marker, и
> контроллер сломанной C копировал СЕБЯ в LKG, уничтожая рабочую копию.
> `handleAsset` при отсутствии ассета в LKG падал в общий cache/network и мог
> смешать страницу B со скриптами C. `restorePreviousBuild()` перезагружал по
> таймеру, не зная, включилось ли восстановление. Кнопка восстановления жила в
> основном бандле и была недостижима при hard-startup ошибке.

- **Build identity.** `arch:startup-ok` продвигает V в LKG только при строгом
  совпадении `msg.build` с текущей сборкой SW (`buildMatchesCurrent`). Маркер
  чужой/старой сборки отклоняется с `build-mismatch`, LKG и режим
  восстановления не меняются. Сценарий «C broken → recovery B →
  startup-ok(B)» проверен: LKG остаётся B, recovery остаётся включён; только
  собственный маркер C после реального успешного старта продвигает C.
- **Fail-closed.** В режиме восстановления навигация и same-origin ассеты
  обслуживаются ТОЛЬКО из LKG. Отсутствующий в LKG ассет приложения даёт
  контролируемый ответ 503 «Режим восстановления», а не сломанный V и не
  свежий network-бандл; сеть для ассетов приложения не используется. Страница
  B не может получить скрипт C.
- **ACK.** `swRequest()` — запрос к SW через MessageChannel с таймаутом.
  Reload разрешён только после ответа `{ ok: true }`; `no-last-known-good`,
  таймаут, отсутствие контроллера или отрицательный ответ отменяют
  перезагрузку с точной причиной. То же для выхода из восстановления.
- **Независимый bootstrap.** В `index.html` ДО основного бандла живёт
  самодостаточный recovery bootstrap: ловит ранние ошибки, через 9 секунд
  проверяет маркер `__archAppStarted` (выставляется ПОСЛЕДНЕЙ строкой
  app.js — syntax error всего файла оставляет его пустым), при упавшем старте
  и существующем LKG показывает минимальный DOM-UI и по явному действию
  пользователя выполняет restore-lkg с ACK. Не использует ни одной функции
  app.js, не читает DB и пользовательские данные. Проверен исполнением
  извлечённого из index.html кода в песочнице БЕЗ app.js.

Ограничение **L-DEPLOY-NO-AUTO-ROLLBACK** сохраняется: переключение остаётся
явным действием пользователя, а не происходит само.

## 7. AI provider hardening

- **Ключ Gemini ушёл из URL** в заголовок `x-goog-api-key`. В query string он
  попадал в referrer, историю и логи любого прокси.
- **Таймаут** для Gemini и OpenAI через общий `_aiFetch()` с `AbortController`
  (60 с). Ошибки нормализованы: `timeout` и `offline` — разные состояния.
- **Схема реально передаётся** (`responseMimeType` + `responseSchema`).
  Несовместимая схема (`oneOf`/`allOf`/`$ref`/…) вызывает **явный отказ до
  отправки запроса**, а не тихий обычный запрос под видом структурированного.
- Новых провайдеров не добавлено.

## 8. Секреты и приватность

- Ключи не попадают в URL, тело запроса, логи, диагностику и собранный бандл —
  проверено тестами по реальному артефакту `dist/`.
- Диагностический отчёт состоит **только** из версий, счётчиков и кодов.
  Тест кладёт узнаваемые «личные» строки во все чувствительные места
  (дневник, симптомы, отношения, моменты, данные рождения, AI-ключ) и требует
  ноль совпадений в JSON отчёта.
- В тестах не используются реальные секреты.

## 9. Профильная изоляция

Заведён реестр `PROFILE_SCOPED_CACHES`. `switchProfile()` вызывает один
`resetProfileScopedCaches()` вместо набора разрозненных вызовов — именно так и
появился дефект изоляции в Волне 4.1. Зарегистрированы:
`astroSourceProjection`, `synthesisRenderState`. Тест требует, чтобы
`switchProfile` не содержал ручных сбросов.

## 10. Release metadata

`BUILD_ID` / `BUILD_SHA` / `BUILT_AT` — плейсхолдеры в `app.js`, подставляемые
**единственным местом**, `build.mjs`. Руками нигде не дублируются; сборка
падает, если плейсхолдер остался незаменённым. `releaseInfo()` отдаёт также
schema, версию SW, версии backup-конверта и астродвижка. Несобранный запуск
честно помечается `injected: false`, а не выдаёт выдуманную версию.

## 11. CI release gate

Новый job `npm run test:artifact` проверяет **собранный `dist/`**, а не
исходники: секреты в бандле, ключ Gemini в query string, незаменённые
плейсхолдеры, полноту app shell в service worker (каждый файл `SHELL` обязан
существовать — `addAll` стоит под `.catch()` и молча проглатывал бы пропажу),
наличие deploy-recovery в выпускаемом SW и SHA-256 критических ассетов.

## 12. Schema / backup

**Schema не изменена — остаётся 5.** Миграции нет. Backup core не переписан:
доказанного дефекта в нём не нашлось, а трогать принятый криптографический код
без причины запрещено. `npm run test:backup` — 8/8 сюит зелёные.

## 14. Известные ограничения

- **L-DEPLOY-NO-AUTO-ROLLBACK** — на GitHub Pages автоматический откат
  невозможен; реализовано сохранение last-known-good и health marker, но
  переключение остаётся за пользователем.
- **L-STORAGE-NO-GUARANTEE** — `navigator.storage.persist()` не гарантирует
  сохранность: ОС вправе очистить данные. Резервная копия — основная защита.
- **L-STORAGE-ESTIMATE-COARSE** — `estimate()` даёт приблизительные значения и
  округляется браузером; размер DB считается по длине строки, не по байтам.
- **L-MEDIA-BYTES-UNMEASURED** — объём медиа отдельно не измеряется (осознанно:
  иначе пришлось бы читать все блобы).
- **L-WEBKIT-OFFLINE-RELOAD** — унаследовано: headless WebKit не поддерживает
  offline reload, проверяется присутствие модулей в SW-кэше.

## 15. Осознанно отложено

Не сделано в этом PR и **не выдаётся за сделанное**. Каждый пункт — отдельная
задача с понятной границей:

| Тема | Что осталось | Почему отложено |
|---|---|---|
| Plain export/import | Продуктовое решение о статусе plain-экспорта, предупреждения, schema-валидация импорта, prototype pollution, частичный импорт, коллизии id | Требует продуктового решения владельца, а не технической правки; затрагивает пользовательский сценарий целиком |
| Encrypted backup hardening | Матрица совместимости версий конверта, дополнительные проверки KDF/алгоритмов, поведение при прерванном restore | Доказанного дефекта не найдено; переписывать принятый крипто-код без причины запрещено |
| Media GC и tombstone undo | Полный аудит orphan GC, shared refs, окна отмены удаления | Диагностика орфанов уже добавлена (read-only); сам GC — отдельная задача с риском потери данных |
| Обновление UI service worker | Экран «доступна новая версия / используется offline / восстановление» | Требует UX-решения; текущий тост сохранён без изменений |
| Производительность | Замеры на 100k событий, прогресс и отмена тяжёлых операций | Не блокирует выпуск; нужен отдельный бенчмарк-харнесс |
| Observability | Локальный технический журнал версий/статусов | Диагностический отчёт уже покрывает основное; журнал — расширение |
