> EXECUTION CONTRACT — комментарий `5227925639`.

>
> Волна 6 позволяет перенести в «Архитектор» работу, проделанную вне
> приложения (сессии в ChatGPT, материалы из Google Drive), **не создавая
> второй модели жизни**. Внешняя сессия = provenance/audit-конверт + проекция
> в уже существующие канонические типы.

## 1. Принцип, от которого нельзя отступать

Импортируемые данные становятся **обычными записями приложения**. Никаких
«внешних инсайтов», «внешних снов» и параллельных коллекций не появляется:
инсайт из ChatGPT — это тот же `DB.insights`, что и написанный руками, с той же
схемой и теми же экранами. Единственное отличие — дополнительное поле `ext`
(provenance), которое отвечает на вопрос «откуда это взялось и чьи это слова».

Отсюда два следствия, зафиксированных тестами:

- импортированная запись участвует в Unified Intelligence (Волна 4) ровно как
  ручная — отдельного «канала внешних данных» нет;
- журнал импортов **не является источником событий** (см. §4).

## 2. Формат пакета `architect-external-work-v1`

Импорт строго локальный: **без сети, без AI-вызовов, без Google OAuth/Drive
API**. Приложение принимает файл или вставленный JSON.

```
{
  format:   "architect-external-work-v1",
  source:   { kind, label, module, chatId },     // kind ∈ 4 значения
  session:  { clientRef, summary, date },
  entities: [ { clientRef, type, sourceId, sourceDate, claimClass,
                textOrigin, relatedSourceIds, data:{…} } ],
  links:    [ { from, to, relation } ]           // relation ∈ PSY_LINK_RELATIONS
}
```

- `clientRef` — идентификатор записи **внутри пакета**; обязателен и уникален,
  иначе связи неоднозначны. При импорте заменяется настоящим `id` приложения.
- `sourceId` — идентификатор исходного объекта в системе-источнике. Это ключ
  provenance-дедупликации (§5).
- `source.kind` ∈ `chatgpt`, `google_drive`, `claude`, `other`.

### Границы пакета (`EXT_LIMITS`)

| Параметр | Значение |
|---|---|
| `maxBytes` | 2 МБ исходного текста |
| `maxEntities` | 500 |
| `maxLinks` | 1000 |
| `maxString` | 20 000 символов на любую строку |
| `maxDepth` | 12 уровней вложенности JSON |

Валидация **fail-closed**: любая неизвестная или опасная конструкция — ошибка,
а не «почистим и поедем дальше». На этапе валидации мутаций базы нет вовсе.

## 3. Целевые типы — только существующие коллекции

`EXT_TARGETS` (9 типов) отображает тип пакета в **реальную** коллекцию:

| Тип в пакете | Коллекция |
|---|---|
| `insight` | `insights` |
| `why` | `whys` |
| `pattern` | `patterns` |
| `dream` | `dreams` |
| `spiritual` | `spiritual` |
| `evolution` | `evolution` |
| `relationshipContext` | `relationshipContexts` |
| `moment` | `moments` |
| `sphereLog` | `sphereLogs` |

Неподдерживаемый тип отклоняется в предпросмотре — молча enum не расширяется.

### Что адаптеры отказываются делать

Каждый адаптер сам решает, достаточно ли материала, и возвращает либо запись,
либо **явную причину отказа**. Ключевые запреты:

- **`moment`** создаётся только из явного self-report: нужны числовые
  `valence` и `activation` в диапазоне 0–100. Состояние **не выводится из
  текста** — иначе интерпретация превратилась бы в измерение.
- **`sphereLog`** требует существующей в этом профиле сферы и явно переданного
  `value`. Числа не выдумываются.
- **`dream`**: источник истины — оригинальный рассказ (`body`). Трактовка
  **не подменяет** текст сна, она кладётся в отдельное поле `arch`, как и в
  ручной форме.

> Замечание по точности: описание в issue #160 предполагало у снов поля
> `title/text/symbols/tone`. Реальная production-схема — `title/body/tone/arch`.
> Адаптер написан по коду, а не по тексту задачи.

### Поля, которые payload задавать не вправе

`EXT_RESERVED_FIELDS`: `id`, `_u`, `sv`, `_del`, `__ts`, `ext`, `createdAt`,
`day`, `kType`, `verif`, `life`, `privacyClass`. Плюс `EXT_POLLUTION_KEYS`
(`__proto__`, `constructor`, `prototype`) — отклоняются fail-closed.
Внешний пакет не может назначить себе `id`, подделать `sv`/`ext` или записать
надгробие в `_del`.

## 4. Журнал `externalWorkSessions` — и почему он НЕ источник событий

Схема поднята `SCHEMA_VERSION` 5 → **6**, аддитивно: одна новая коллекция в
`DEFAULT_DB` и в `IDCOLS` (теперь 26). Существующие данные не мигрируются и не
переписываются.

Журнал хранит **только аудит**: источник, модуль, chatId, дата сессии, время
импорта, `contentHash`, краткое резюме, счётчики принятого/отклонённого и
ссылки `recordRefs`/`linkRefs` на созданные объекты. Он **не хранит полный
transcript** и не дублирует canonical-тексты.

`externalWorkSessions` **отсутствует в `EVENT_SOURCES`** сознательно. Если бы
журнал порождал события, одно и то же содержание считалось бы дважды: как
canonical-запись и как «была сессия импорта» — и корреляционный движок Волны 4
получил бы двойное evidence на пустом месте. Это закреплено и обычным тестом,
и mutation-проверкой (§8).

`id` журнала — namespaced строка `externalWork:*` (тот же приём, что
`psyLink:*`/`relctx:*` после owner review PR #149): общий для всех коллекций
механизм надгробий остаётся глобальным, но структурно не может задеть чужую
запись с совпавшим числовым `id`.

## 5. Дедупликация: два уровня, и ни одного по тексту

| Уровень | Ключ | Что ловит |
|---|---|---|
| Пакет | `contentHash` — SHA-256 по канонизированному JSON | повторный импорт того же пакета целиком |
| Запись | `sourceId` в разрезе целевой коллекции | тот же исходный объект, пришедший другим пакетом или из другого модуля |

Канонизация сортирует ключи и отбрасывает `undefined`: один и тот же пакет с
другим порядком ключей обязан дать **тот же** хеш.

**Дедупликации по тексту нет и не будет.** Два разных события, описанных
одинаковыми словами, остаются двумя записями — иначе приложение начало бы
терять факты, совпавшие формулировкой.

Когда `sourceId` уже импортирован, новая запись не создаётся, но её id
**переиспользуется для связей** — то есть повторный пакет может достроить
связи к уже существующим записям, не плодя дублей.

## 6. Транзакционность и границы Волны 5

Предпросмотр строится на **клоне** `DB`: адаптеры, валидация связей и дедуп
работают ровно на тех данных, которые получатся после коммита, а живой `DB` не
трогается вовсе. До подтверждения пользователем — ноль мутаций.

Коммит собирает кандидата на клоне, валидирует его целиком и только потом
делает один безопасный `persist()`. Любая ошибка — **zero mutation** всего
batch: ни одной записи, ни одной связи, ни строки журнала.

Импорт **не обходит** механизмы Волны 5:

- под recovery-блокировкой (`isWriteLocked()`) импорт запрещён и честно
  сообщает об этом;
- запись идёт через транзакционный `persist()`/`_txWrite()` со снапшотом и
  откатом при сбое.

## 7. Связи: один production-валидатор, без параллельных правил

Связи создаются тем же `validatePsyLink()`, что и вручную. Для Волны 6 он
получил необязательный параметр `db`, чтобы **один и тот же** валидатор работал
и на живой базе, и на транзакционном кандидате импорта. Параллельной копии
правил не заведено — это было бы вторым источником истины.

Отбраковка происходит на двух уровнях: схема пакета отсекает неизвестное
`relation`, а сам валидатор — неверную пару коллекций, self-link и orphan.
Отбитая связь не мешает импортировать записи пакета: отклоняется именно связь.

Все фикстуры синтетические (`TEST-LIFE-*`, `TEST-DREAM-*`, `TEST-PARA-*`).
Отдельный сценарий сканирует саму сюиту и падает, если в неё попадёт реальный
`LIFE/DREAM/PARA`-идентификатор; там же проверяется, что сканер вообще способен
отличить реальный id от синтетического.

### Mutation sanity

Зелёная сюита сама по себе не доказывает, что проверки что-то ловят. Каждая из
пяти защит по очереди снимается в собранном бандле, и соответствующий сценарий
**обязан** покраснеть:

| Мутация | Ожидаемое падение |
|---|---|
| снят provenance-дедуп | «один факт остался одним canonical-фактом» |
| коммит пишет прямо в живой `DB` вместо клона | «zero mutation» |
| снята валидация связей в предпросмотре | «отбита production-валидатором» |
| журнал добавлен в `EVENT_SOURCES` | «`EVENT_SOURCES`» / двойное evidence |
| снята recovery-блокировка Волны 5 | «recovery-блокировкой» |

Проверка требует не просто «сюита упала», а падения **именно того** сценария,
который сторожит снятую защиту.

### Что ещё покрыто сквозной сюитой

Идемпотентность и повторный импорт; изоляция профилей (2 → 0 → 2);
sync A→B с сохранением provenance и связей; отсутствие сетевых и AI-вызовов при
импорте (0/0); prototype pollution и попытки задать служебные поля; XSS в
предпросмотре (внешний текст рендерится экранированным, но в хранилище лежит
как есть — экранирование на рендере, не в данных); a11y и вёрстка экрана
импорта на iPhone; отсутствие JS-ошибок за прогон.

## 9. Приватность

- Импорт не делает ни одного сетевого запроса и ни одного AI-вызова.
- Журнал помечен `privacyClass: 'sensitive'`.
- В зашифрованной копии открытыми остаются только `format`, `envelopeVersion`,
  `kdf`, `cipher`; резюме сессии, `sourceId`, `chatId`, `contentHash` и id
  журнала не встречаются в файле копии ни в каком виде (проверено тестом).
- В репозиторий не попадают реальные личные данные — только синтетические
  фикстуры.

## 10. Известные ограничения (осознанные)

1. **`spiritual` не входит в `EVENT_SOURCES`** — это ограничение существующего
   движка Волны 4, а не импорта. Импортированная духовная практика видна на
   своём экране, но не участвует в корреляциях. Копий в `insights` «ради
   видимости» не создаётся: это исказило бы и evidence, и смысл записи.
   Включение `spiritual` в источники событий — отдельное решение владельца.
2. **`pattern` не получает отдельного detail-экрана** — как и в Волне 1.
3. **Google Drive не подключается программно.** Импорт принимает файл или
   вставленный JSON; OAuth/Drive API сознательно не реализованы (это выход за
   privacy boundary и потребовал бы отдельного контракта).
4. **Ручная сборка пакета.** Конвертера «сырой экспорт ChatGPT →
   `architect-external-work-v1`» в приложении нет; пакет готовится вне его.

## 11. Что сознательно отложено

- Автоматическое разрешение конфликтов при повторном импорте с изменённым
  содержанием (сейчас: тот же `sourceId` — переиспользование, не обновление).
- Редактирование provenance после импорта.
- Массовый импорт нескольких пакетов одной операцией.
