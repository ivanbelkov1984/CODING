# Wave 4.1 — Astrology × Pattern Engine Integration

> issue [#157](https://github.com/ivanbelkov1984/CODING/issues/157). База — `MAIN`
> `72315e81a049316afe3be68aaec84590f2f39277` (merge-commit Волны 3, PR #155).
>
> Это **не новая астрологическая волна**. Расчёты завершены Волной 3 и там же
> проверены. Здесь астрология подключается к уже существующему движку
> «Закономерности» как **ещё один источник временных совпадений** — и ничего
> больше.

## 1. Архитектура

Один поток событий, один движок корреляций, один источник астрособытий.

```
DB-коллекции ──► EVENT_SOURCES ──┐
                                 ├──► unifiedEvents(days) ──► findCorrelations()
DB.astroBirth ──► astroEventProjection() ──► astroSourceEvents(days) ──┘        └─► synthesisStats()
                        (Волна 3, единственный источник)                        └─► findRecurringSequences()
```

**Точка подключения — ровно одна:** `unifiedEvents()` дописывает
`astroSourceEvents(days)` в тот же массив, что и события коллекций, после чего
поток сортируется по времени как единое целое. Специальных путей нет: всё, что
ниже по конвейеру (корреляции, статистика, последовательности, цепочки,
сферы, отношения, overview), получает астрологию тем же способом, что и
здоровье, психологию, моменты и остальное.

Ничего не пересчитывается. `astroSourceEvents()` только вызывает проекцию
Волны 3 и приводит её события к форме общего потока.

## 2. Event mapping

| Поле | Значение | Комментарий |
|---|---|---|
| `id` | `astro:transit:<пара>:<дата пика>` | стабильный id прохождения из Волны 3 |
| `source` | `astro` | новое поле; события коллекций получают `db` |
| `type` | `astro_transit_aspect` | тип события проекции |
| `date` | дата пика | суточная дискретизация |
| `time` | полдень-UTC этой даты | якорь дня, **не** заявка на точное время (см. §3) |
| `tags` | `astro:transit:*`, `astro:aspect:*`, `astro:natal:*` | только расчётные факты |
| `importance` | 1–3 по орбису | из проекции |
| `sourceCollection` | `astroBirth` | |
| `referenceId` | `<пара>:<дата пика>` | **уникален на событие** (см. §6) |
| `methodologyId` | `western-tropical-v1/transit-orbs-v1(3)` | |
| `confidence` | `medium` / `low` | `low` при неизвестном времени рождения |
| `provenance` | движок, версия проекции, орбис, признак пика, `birthTimeKnown`, `projectedTime` | |

Ничего не потеряно: все поля проекции доходят до потока.

## 3. Честность суточной дискретизации

Проекция Волны 3 сознательно не заявляет точное время аспекта (`time: null`).
Общий поток требует числовое время для сортировки и оконных расчётов, поэтому
астрособытие получает **тот же полдень-UTC якорь**, который production уже
применяет к любым записям, у которых есть только день. Исходная честность
сохранена: `provenance.projectedTime === null` — и это проверяется тестом.

## 4. Read-only

Проекция существует **только во время анализа**:

- новых коллекций, IndexedDB-хранилищ, schema, кэшей на диске, persistence,
  backup- и sync-путей **не создано**;
- `DB` не изменяется анализом — проверено тестом (сериализация `DB` до и после
  `unifiedEvents()` + `synthesisReport()` идентична);
- единственное состояние — `_astroSrcCache` (переменная модуля, не
  персистируется) и `_synLastAstroEvents` (сбрасывается каждым рендером).

## 5. Производительность

`astroEventProjection()` вызывается **ровно один раз на анализ** — проверено
тестом, который подменяет функцию счётчиком и прогоняет `synthesisReport()`.
Кэш анализа (`_astroSrcCache`) ключуется профилем, окном, признаком
включённости и отпечатком данных рождения; при любом расхождении — пересчёт.

## 6. Защита от дублей

- `id` уникален на прохождение (пара + дата пика) — из Волны 3;
- **`referenceId` сделан уникальным на событие.** Раньше он был константой
  `'astroBirth'`, и ключ записи Pattern Engine `sourceCollection:referenceId`
  совпал бы у ВСЕХ астрособытий: они выглядели бы одной записью, а evidence
  схлопывался бы в одну. Теперь ключ различает события;
- одно физическое прохождение сохраняет тот же `id` и ту же дату пика в
  перекрывающихся окнах — проверено;
- **same-record:** одно астрособытие всегда даёт три тега сразу
  (`transit`/`aspect`/`natal`). Без регистрации это была бы гарантированная
  тавтология — ровно та, против которой Волна 4 вводила `TAG_FAMILY_SETS`.
  Источник добавлен в существующий реестр отдельным семейством `{'astro'}`;
  сама логика same-record не менялась. Проверено тестом: пар вида
  «оба тега астрологические, совпадение в тот же день» — ноль.

## 7. Ядро корреляций не изменено

Fisher (двусторонний), Benjamini-Hochberg, `SYN_FDR_ALPHA = 0.05`, baseline,
enrichment-only гейт (`hits ≥ minSamples && lift ≥ 1.3 && significant`),
`minLag`, depletion-политика — **без единого изменения**. Астрология проходит
через тот же гейт, что и любой другой источник. Проверено тестами, которые
читают реальный текст `findCorrelations` и константы.

## 8. Эпистемология

Астрология — источник **временных совпадений**, не доказательство причинности.

Запрещённые формулировки («Астрология доказала», «Транзит вызвал», «Из-за
Марса», «Поэтому произошло», «Причина») отсутствуют в пользовательских
текстах — проверено тестом по реальным строкам, которые видит пользователь.

Разрешённый словарь: «совпало по времени», «наблюдается временная связь»,
«символический контекст», «астрологическое событие», «не доказывает
причинность».

## 9. Неизвестное время рождения

Проекция Волны 3 уже исключает события, зависящие от домов и углов, и понижает
уверенность до `low`. Интеграция это сохраняет и проверяет: планетарные события
остаются, событий с домами/углами нет, `provenance.birthTimeKnown === false`.

## 10. Настройка

`correlationSettings.useAstro` — **по умолчанию выключено**, в том числе для
существующих профилей: у них в сохранённом скаляре ключа нет, чтение даёт
`undefined` → falsy. Поэтому **миграция не нужна и `SCHEMA_VERSION` не
поднимается** — это добавление поля в уже существующий скаляр, который
backup/sync переносят целиком и генерично.

UI на экране «Закономерности»: переключатель «Использовать астрологические
события» с подписью «Символический источник. Используется только при поиске
временных совпадений. Не доказывает причинность.»

Каждое совпадение с участием астрологии несёт бейдж «✦ Астрология» и кнопку
«Подробности», открывающую панель с методологией, движком, датой пика,
орбисом, уверенностью и признаком «известно ли время рождения». Без трактовок.

## 11. Изоляция профилей

Кэш проекции сбрасывается при смене профиля (`switchProfile`) и при изменении
данных рождения (`saveAstroBirth`); ключ кэша дополнительно содержит id
профиля. Проверено тестом: изменение данных профиля не переиспользует прежние
астрособытия.

## 12. Schema / backup / sync

**Schema не изменена — остаётся 5.** Backup, restore, plain export и merge не
затронуты: `correlationSettings` как был единственным скаляром волны, так и
остался, и переносится генерично. Регрессия `npm run test:backup` подтверждает.

## 13. Покрытие тестами

`tests/wave4-1-astro-pattern-engine.spec.mjs` — **44 блокирующие проверки** в
обычном CI: источник выключен/включён, mapping и полнота полей, честность
`projectedTime: null`, отсутствие данных рождения, неизвестное время рождения,
ровно один вызов проекции, стабильность id, отсутствие дублей (id,
referenceId, между окнами), отсутствие same-record тавтологии, неизменность
ядра (Fisher/BH/alpha/enrichment), schema/backup/sync impact, read-only,
изоляция профилей, отсутствие сети и AI, эпистемология, UI и a11y,
поведение старого профиля без ключа.

## 14. Известные ограничения

- **L-ASTRO-DAILY** — суточная дискретизация: событие привязано к дате пика с
  точностью до суток; под-суточный поиск точного момента не выполняется.
- **L-ASTRO-TRANSITS-ONLY** — источник поставляет только транзитные аспекты к
  натальным телам. Прогрессии, дирекции, возвращения и ведические периоды в
  поток не подаются (проекция Волны 3 их не производит).
- **L-ASTRO-WINDOW-400** — при `days == null` проекция ограничивается 400
  сутками (кап самой проекции).
- **L-ASTRO-NO-HOUSES** — события, зависящие от домов и углов, не производятся
  вовсе, поэтому при неизвестном времени рождения теряется не «часть» потока,
  а ничего сверх уже отсутствующего.
- Наследуются ограничения Волны 3 (L-TZ-MANUAL, L-OBLIQUITY,
  L-AYANAMSHA-LINEAR и остальные) — см. `WAVE3_ASTROLOGY_VERIFICATION_CONTRACT.md`.
